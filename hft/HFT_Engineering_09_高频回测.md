# HFT Engineering 09：高频回测——你的挂单排在哪里，又晚到了多久

程序看到买一价是 100，决定挂一笔 20 手的买单。普通的 K 线回测这时会问一个很简单的问题：后面的价格到没到过 100？到过，这笔单就算成交。高频回测要回答的问题完全不同：这笔单什么时候才到达交易所？到达时前面排着多少手？在它还排在队尾的这段时间里，主动卖出先吃掉了谁，轮不轮得到它？这三件事任何一件变了，成交结果都不一样。

这一篇先从这笔挂单出发，看高频回测和普通 bar 级回测到底差在哪里，再调研几个主流开源方案能做到哪一步，然后依次讲队列位置怎么估计、自己的挂撤单会怎样影响对手、回放时钟怎么推进，最后简短说回测和实盘怎么对齐。

## 1. 同一笔挂单，四种成交结果

先把几个基础词说清楚。按价位汇总推送的盘口叫 L2（Market by Price，MBP），每个价位只给一个总量，看不出这个量由哪些订单组成；逐笔订单推送叫 L3（Market by Order，MBO），每笔单带订单 ID，新增、成交、撤销都能对应到具体订单。同一价格上先到先得的规则叫先进先出（First In, First Out，FIFO），你的单前面压着多少手，就是你的队列位置。

构造一个最小的合成场景。价格 100 的买方队列里，A 先挂了 40 手，B 在 A 后面挂了 20 手，我方的 20 手最后到达，排在队尾：

[![价格 100 的买方队列从队头到队尾依次是 A 40 手、B 20 手、我方 20 手](https://raw.githubusercontent.com/Obscurepawn/TradingSystemLearning/main/hft/assets/hft-09/queue-example.png)](https://raw.githubusercontent.com/Obscurepawn/TradingSystemLearning/main/hft/assets/hft-09/queue-example.png)

后面市场里发生几笔主动卖出和一次撤单。只改变回测采用的假设，这同一笔 20 手买单会得到完全不同的账本：

| 回测假设 | 我方最终成交 |
|---|---:|
| 看到成交价等于 100，就把 20 手全部记为成交（错误基线） | 20 手 |
| 按 FIFO 排队，保留行情与订单延迟，撤单在途期间仍可能成交 | 15 手 |
| 把网络延迟设为 0，撤单更早生效 | 5 手 |
| 订单晚到入队，错过前面的主动卖出 | 10 手 |

第一行是最常见的错误：历史里那笔 100 的主动卖出全部由 A 承接，回测却把同一份主动量又分给了我方，等于一笔流动性被用了两次。第二行是完整的排队过程：先消耗 A 的剩余，再轮到我方成交一部分，剩下的继续排队，撤单请求到达交易所之前又成交了一笔。第三行里撤单更早生效，后面的主动卖出轮不到这笔单。第四行更直接：订单到得太晚，之前的成交已经结束，它没有资格追认。

这几种结果的差别不是统计噪音，而是这笔策略最后持有 5、10、15 还是 20 手。库存不同，下一步的报价、对冲和风险额度全都跟着变。bar 级回测默认“价格到过就能成交”，把队列、延迟、在途状态这些决定成败的细节全部压成一个滑点系数；高频策略里，几微秒和几手的差别会被后续决策放大，所以回测必须先把成交这件事本身模拟对，盈亏曲线才有意义。

## 2. 主流开源方案调研与对比

动手造引擎之前，先看看社区里已经有什么。下面的事实都核对过各项目的官方文档和仓库，只描述能力边界，不跑分，也不引用未经实测的性能数字。

hftbacktest（nkaz001）是一个市场数据回放式的高频回测工具，Rust 核心加 Python 策略接口（策略用 numba 即时编译）。它支持 L2 价位总量数据，也支持 L3 逐笔订单数据，官方教程以 DataBento 的 CME MBO 数据为例。队列模型是它的核心组件：L3 直接按订单数据确定位置，L2 用概率队列模型估计。延迟提供常数、实测订单延迟插值、由行情延迟派生三种。官方文档写得很明确：这是回放，你的订单不能改变被回放的市场，不考虑市场冲击，基本假设是你的单小到不足以影响市场。它没有多智能体。适合在加密货币等 MBP 数据上研究被动挂单、做市排队和执行细节。

NautilusTrader 是 Rust 原生核心、Python 做控制面的交易引擎，回测和实盘跑在同一套事件驱动架构上，同一份策略代码不用重写。回测支持 quote tick、trade tick、bar 和 L1/L2/L3 订单簿数据，时间分辨率到纳秒。撮合把历史订单簿视为不可变：模拟成交不会扣减历史簿，引擎用消耗量跟踪（liquidity consumption）记录每个价位已被模拟订单用掉多少；开启 queue_position 后用盘口加成交数据跟踪展示队列，没有队列数据时用 prob_fill_on_limit 做概率近似。它同样不建模内生冲击，也没有多智能体。它的定位是多资产、多场所，需要把研究结果平滑搬到实盘的中高频工程系统。

ABIDES（JPMorgan 开源，BSD 许可）和前两类不是一个东西。它全称 Agent-Based Interactive Discrete Event Simulation，是多智能体离散事件模拟环境，Python 实现。一个交易所 agent 维护连续双向拍卖簿，背景由大量 agent 组成：参考配置 RMSC03 里有 100 个按基本面贝叶斯定价的 Value agent、25 个动量 agent、5000 个随机方向的 Noise agent，再加一个按成交量百分比报价的做市 agent（做市就是同时在买卖两侧挂单、赚价差、自己承担库存风险的角色）。每个 agent 之间、agent 与交易所之间可以单独配网络延迟，消息设计参考 NASDAQ 公开的 ITCH/OUCH 协议。市场是 agent 行为涌现出来的，它不回放某一天的历史行情，因此可以做反事实实验：同一个随机种子，加一个执行 agent 和不加，对比中价位移多少。它适合研究冲击和对手反应，不适合回答“我的策略在 2024 年某一天赚了多少”。

另外几个常见项目要说明定位，避免误用。Hummingbot 是实盘优先的加密做市框架，内置 dashboard 回测跑在 K 线上，按设定的时间分辨率取 OHLCV，价格穿越即推断成交，没有逐笔队列引擎，也不建模微秒延迟，适合参数粗筛。Lean 是 QuantConnect 的引擎，C# 实现、支持 Python/C# 策略，属于组合级事件引擎，bar/tick 驱动，提供 fill model 和滑点模型，滑点里有按成交量比例计算的冲击项，但回测中市价单默认立即全额成交，不逐单跟踪队列优先级，适合股票、加密的中低频组合研究。Backtrader 是经典的 Python bar 驱动框架，成交用固定百分比或固定点数滑点处理，没有队列、没有延迟模型，适合日线和分钟级原型。

| 工具 | 数据粒度 | 队列位置模型 | 延迟模型 | 冲击 / 多智能体 | 语言与形态 | 适用场景 |
|---|---|---|---|---|---|---|

这张表读下来有一个明确的结论：没有一个开源工具同时把“精确排队执行”和“内生市场反应”都解决掉。选工具之前先想清楚要回答哪个问题——是评估一笔挂单在既有市场流里怎么成交，还是评估我的大单会怎样改变市场。前者用回放，后者要么加冲击模型，要么上多智能体。

## 3. 只有 L2 数据时，怎么估计自己的队列位置

L3 场景下这件事很直接。每笔单有 ID，我方订单入队时把它插进有序链表，前面的数量就是初始队列位置；该价位成交时按 FIFO 从队头往后扣，撤单按 ID 直接从链表摘除，我方位置随之前进。hftbacktest 的 L3 FIFO 队列模型走的就是这条路，不需要任何概率假设。

麻烦的是 L2。价位总量下降了，你只看到“少了 d 手”，不知道这 d 手是在你前面撤的还是后面撤的。前面撤，你的位置前进；后面撤，原地不动。两种情况对成交概率的影响完全相反，而历史数据里没有这个信息，只能估。

估计分三步。第一步是入队时的初始位置：发单时记一次该价位总量，收到交易所接受确认时再看一次，用确认时刻的总量减去我方数量作为前方估计，两个时刻也可以取平均，因为行情本身有延迟，发单时刻看到的盘口未必是订单真正入队时的盘口。第二步是成交推进：该价位出现一笔成交价等于该价位的主动成交，FIFO 下先消耗前方，能确定地把前方量往前推，推到我方才轮到成交。第三步是处理匿名减量：一次撤单或改单导致总量下降、又无法分辨前后时，按概率把这份减量分配到前方和后方。

hftbacktest 的官方队列模型文档把这件事分成两类。RiskAverseQueueModel 是最保守的模型：撤单和改单只发生在队尾，我方位置纹丝不动，只有该价位真实成交才让位置前进，给出的是成交概率下界，适合先求稳健。另一类 ProbQueueModel 是概率模型族，按当前队列位置决定一份减量落到前方的概率，内置幂函数族 PowerProb（不同指数给出不同的概率轮廓）和对数族 LogProb（f=log(1+x)，轮廓随该价位总量变化）。概率形式可以写成：前方量 Vf、后方量 Vb，一份减量落到前方的概率 p = f(Vf) / (f(Vf) + f(Vb))，f 是递增函数；队头时 p=0（减量必然在身后），队尾时 p=1（减量必然在身前），边界是自然满足的。这个思路来自社区对 MBP 队列估计的经典讨论，f 取恒等函数、平方根、幂或对数，对应不同的保守程度，理想情况下 f 应该用自己的真实成交数据去拟合。

[![L2 只能看到价位总量：我方前方 Vf 和后方 Vb 都未知，一份匿名减量以概率 p 落到前方、以 1−p 落到后方](https://raw.githubusercontent.com/Obscurepawn/TradingSystemLearning/main/hft/assets/hft-09/l2-queue-estimate.png)](https://raw.githubusercontent.com/Obscurepawn/TradingSystemLearning/main/hft/assets/hft-09/l2-queue-estimate.png)

```text
# L2 队列位置估计（伪代码）
# 入队：用确认时刻的价位总量减去我方数量作为前方估计
front = max(price_level_qty_at_ack - my_qty, 0)
behind = 0

每一次该价位更新:
  if 主动成交价等于该价位，成交量 v:
      # FIFO：确定地先消耗前方
      consumed = min(front, v)
      front   -= consumed
      my_fill += min(my_remaining, v - consumed)
      my_remaining -= my_fill
  elif 匿名减量 d（撤单/改单，无法分辨前后）:
      # 概率模型：把 d 按 p 分配到前方
      p = f(front) / (f(front) + f(behind))
      front_cut = sample(d, p)          # 落到前方的量
      front  -= front_cut
      behind -= (d - front_cut)
```

RiskAverse 就是上面伪代码里 p 恒等于 0 的特例。概率模型有随机性，单次抽样只给一个点估计，正式评估时固定随机种子跑多个样本，统计成交量和首次成交等待时间的分布，而不是只看一次的数字。

校准这件事不能只看总成交率。两个模型可能都调出 30% 的总体成交率，却把成交给了完全不同的订单子集。正确的对法是按盘口深度、等待时长、波动、订单大小分组，比较每一组的成交概率和等待时间分布。还要留意逆向选择（adverse selection）：被动挂单更容易在价格即将朝自己不利方向走的那一刻成交，成交多未必是好事，可能只是来不及撤掉的单接住了坏价格，这要靠成交后的 markout 分开看。

L2 估计还有一个结构性盲区：冰山单（hidden/iceberg order，只露出一部分数量，成交后再补挂出隐藏量）。可见深度里看不到它的真实体量，它在队列里的优先级规则也因交易所而异，概率模型只能把它并入未知量，没法还原。L3 数据也不是万能，官方教程自己就提醒，CME 的 L3 深度不包含隐含订单，回测结果最终仍要拿实盘验证。

## 4. 自己的挂撤单会怎样影响对手盘

回放式回测有一个绕不开的前提：历史行情是一个“没有我”的世界。文件里 B 在某一时刻撤单、某笔主动卖出在某个价位发生，这些事件写死后就不再变，我方挂 1 手还是 200 手，B 都在同一时刻撤掉同样的数量。这一节说的就是这个前提在哪里失效。

第一层是直接冲击，机械层面的。主动单吃掉对手深度，盘口和队列立刻改变；被动单挂进去，可见量增大，买卖盘的不平衡也跟着变。在回放里这些改写都不发生，历史簿保持原样。订单规模相对深度越小，这个近似越安全；一旦你的单大到能被看见，问题就进入第二层。

第二层是反身性：对手的挂撤单行为本身可能因为你的行为而改变。别人看到盘口出现一笔大单，可能抢在你前面排队，可能赶紧撤掉自己的单，做市商看到不平衡会调整两侧报价，甚至换价避让。历史文件里的那个 B，在真实世界里看到我方 20 手入队之后，未必还会执行原来的撤单计划。更尖锐的问题出现在主动成交：假设我提前买走了历史里的订单 X，随后历史又要求 X 被别人撤掉、或被另一笔主动单成交，这时模拟器手里已经没有这笔单，继续忽略无效事件、把数量夹到零，价格和订单流就悄悄偏离了原始历史。

固定历史回放捕捉不到这些反应，社区里常见的处理办法有四种，各有各的局限。

最轻的做法是保守假设加冲击模型。小单直接假设无冲击；大单引入成本模型。经验上观察到价格冲击大致随参与成交量的平方根增长（平方根冲击律），冲击又分暂时性（成交后价格回落的部分）和永久性（被信息改变、不再回落的位移）。Almgren-Chriss 的经典思路把冲击成本和执行风险放进同一个优化：想快，承担更多冲击成本；想慢，承担更多价格暴露风险，拆单路径在两者之间取平衡。局限要说清楚：平方根是经验规律不是物理定律，跨市场、跨规模并不稳定；模型参数必须从自己的成交数据估，套一个默认系数出来的成本只是拍脑袋；它修正的是成交价格，修不了对手行为的改变。

再往上一层是多智能体模拟，以 ABIDES 为代表，让背景 agent 真的对我的行为做反应，跑反事实对比。它的局限同样明显：背景 agent 的行为规则和参数全是假设，先得让合成市场的价差、深度、成交强度、撤单强度、价格波动这些统计量接近真实，否则产出的反应本身就是错的；一个能生成热闹订单簿的环境，如果在大买盘出现时诱导出错误方向的订单流，只会把策略排序带偏。而且它算得贵，适合回答“冲击大概多大、方向如何”，不适合做逐日绩效评估。

小规模实盘 A/B 测试校准是拿真实世界补模型：用低数量、明确额度上线，只记录不扩量，观察对手的真实反应。局限是样本小、有真实成本和风险，小单测不出大单的冲击，也没法覆盖所有市场状态。

工程上最务实的一步是实盘成交与回测逐笔对账：把回测预测的“会不会成交、何时第一次成交、成交多少、何时知道成交”和私有回报逐笔关联，按流动性、波动、订单大小、队列位置分组找偏差，再回头修队列模型和延迟模型。它的局限是只能修正已经观察到的区间，没经历过的状态外推仍要靠假设。

实际做法通常是组合：队列占比很小、研究重点是延迟和排队，固定历史回放加保守假设就够；单量大、策略依赖对手看到后的反应，再叠冲击模型或选一段做 ABIDES 式反事实，最后用小额实盘和对账收尾。

## 5. 事件驱动回放：两种时钟节奏和三类延迟

高频回测的内核是离散事件模拟。引擎维护一个按时间排序的事件队列，队首事件发生在哪一刻，模拟时钟就直接跳到那一刻，执行入队、撮合、生成回报，再把后续事件排进队列，中间的微秒不需要真的等待。虚拟世界里的延迟保持原值，计算机却可以用远短于真实的墙钟时间跑完一整天。

每个事件至少带两个时间戳。交易所时间戳（exch_ts）记录事件在交易所发生的时刻，本地接收时间戳（local_ts）记录它何时进入策略所在的系统。这两条流的顺序可能不一致：交易所先发生的深度更新，本地可能晚于一笔成交收到。hftbacktest 用 EXCH_EVENT 和 LOCAL_EVENT 两个标志分别维护两条有序流，就是为了处理这种反向。策略只能使用已经送达本地的消息，让策略提前读到交易所侧还没回报的成交状态，就是前视偏差。

回放节奏有两种，目的不同，不要混用。尽快均匀快放（as-fast-as-possible）按事件顺序推进模拟时钟，不等待真实物理间隔，一天的历史几分钟跑完，适合参数搜索和策略研究；它的代价是测不出真实程序的队列积压、内核丢包和处理延迟，因为根本没有真实时间流逝。按墙钟节奏回放（wall-clock）反过来，按真实物理间隔把事件喂给真实程序，用于联调真实网关、压力测试和纸面交易，这时测量到的排队和耗时才是程序自己的表现；代价是跑不快，没法做大规模参数遍历。

延迟模型挂在模拟时钟上，分三类，hftbacktest 的文档把它们分得很清楚：

[![交易所事件经 feed latency 到达本地；本地请求经 order entry latency 进入撮合；撮合后的回报经 order response latency 回到本地](https://raw.githubusercontent.com/Obscurepawn/TradingSystemLearning/main/hft/assets/hft-09/latency-sequence.png)](https://raw.githubusercontent.com/Obscurepawn/TradingSystemLearning/main/hft/assets/hft-09/latency-sequence.png)

feed latency 是交易所发出行情到本地收到的间隔，由双时间戳之差估计；order entry latency 是发出请求到撮合引擎处理的间隔；order response latency 是撮合处理完到本地收到回报的间隔，成交回报也受它影响。模型形式有常数、分布抽样，以及基于实测数据插值。实测订单延迟的采集办法本身有点巧妙：定期提交一批不可成交的订单，记录本地发送、交易所处理、本地收到回报三个时刻，得到一组真实往返样本，IntpOrderLatency 按时间插值取用；没有实测数据时，可以从行情延迟派生一份人工订单延迟。要注意繁忙时段三类延迟往往同时恶化，把三个独立平均数塞进模型会漏掉这种相关性。

策略自身的计算耗时也要计入模拟时钟，不能默认零。串行处理时，第 i 条消息的开始处理时间是到达时间和上一条处理完成时间的较大者，完成时间再加上本条计算耗时；本地已收到而未处理的消息在队列里等着，实盘如果只保留最新报价或批量合并，模拟器要执行同样的合并规则，把忙碌期间的消息悄悄跳过去会改变信号使用的历史。快放模式下，计算耗时是给定的模型输入；实时模式下，它变成被测对象，由性能实验回答程序到底做不做得到。

## 6. 让回测和实盘逐步对齐

最后简短说验证路径。合成事件先把事件调度、数量守恒和状态机跑通，再换真实日志校准延迟、队列和成本，训练区间定参数，验证区间选模型，留出新区间冻结不动，看过结果再调参数就等于把它污染进开发集。

实时影子运行用同一份策略代码，只记录拟发请求、不送交易所，验证输入适配、特征计算和计算耗时；影子单没有真实入队，真实优先级和成交仍要靠后续小额实盘验证。对账的最小单位是一笔逻辑订单：挂单前的盘口、发送记录、接受与撤改结果、全部成交回报、后续价格逐笔串起来，预测成交、首次成交时刻、成交数量分别和实盘比，再按分组找系统性偏差。一次模型修正后，重跑固定的合成账本和历史回归样本，确认该变的订单变了、不该变的保持可解释。

回测不是用来证明策略赚钱的，它是一个能逐笔追问“这笔为什么成交”的账本。队列位置、延迟和冲击这三个假设写清楚、可复现，偏差出现时才知道回去改哪一层。

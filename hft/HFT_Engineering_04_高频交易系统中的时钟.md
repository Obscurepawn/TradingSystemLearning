# HFT Engineering从入门到入土（4）—— 深入理解计算机时钟

判断交易系统快慢之前，有一个问题贯穿整条交易路径：我们用来测量耗时的时间，到底是怎么得到的？

一条行情到达网卡后，程序读取行情、更新订单簿、执行策略，最后发出订单。网卡可以记录收发报文的时间，程序可以在各阶段读取 CPU 计数器，交易所回报里也可能带有自己的时间戳。这些数字虽然都表示时间，起点、单位和生成方式却未必相同。

解释一个时间戳，要知道**它记录了什么事件、由哪个时钟生成、采用什么时间基准，以及存在多大的误差**。这些信息决定了硬件计时、Linux 接口、网络同步和稳定性测量各自要解决的问题。CPU 计数器部分以 x86 TSC 为例。

<a id="sec-1"></a>
## 1. 高频交易系统为什么需要时钟

### 1.1 同一个交易系统，需要回答几种不同的时间问题

分析策略决策时，我们关心计算用了多久；排查跨机故障时，希望把几台机器的日志对应起来；观察一次下单时，则关心从行情到订单的 tick-to-order 延迟。

| 场景 | 具体问题 | 对时钟的主要要求 |
|---|---|---|
| 进程内性能分析 | 更新订单簿和策略计算各花了多久？ | 区间可比较、读取成本低、打点不扰乱热路径 |
| 本机行情到发单 | 行情进入网卡，到订单离开网卡用了多久？ | 收发边界清楚、硬件时间戳可对应 |
| 跨机日志与单向延迟 | A 发出后，B 何时收到？ | 两端时间基准可比较，同步误差足够小 |

### 1.2 从一条行情到一笔订单，先标清测量边界

沿用前文的记号：`H0` 是网卡接收行情的硬件打点，`C0` 是应用取得行情，`C4` 是订单完成风控与编码，`H1` 是网卡发送订单的硬件打点。

![行情到订单的数据路径与时钟域](assets/hft-04/clock-domains-path.png)

`C4 - C0` 覆盖应用内部处理；`H1 - H0` 覆盖本机从接收行情到发出订单的路径。固定测量口径后，优化前后的结果才有可比性。

网卡常使用 PHC（PTP Hardware Clock，精确时间协议的硬件时钟）生成时间戳。如果 `H0`、`H1` 由同一个 PHC 产生，且测量区间没有时钟跳变，通常可以直接计算这两个硬件打点之间的时间。如果 `H0` 来自网卡 A，`H1` 来自网卡 B 的独立 PHC，求差就依赖两只钟之间的关系。至于 `C0 - H0`，当应用使用 CPU 计数器打点时，它已经跨越 CPU 与网卡的时钟域。

## 2. 先分清我们需要哪一种时间

### 2.1 绝对时间、时间间隔与时钟域

绝对时间把事件放到一条公共时间线上，例如日志中的日期与时刻。时间间隔描述两个事件之间经过了多久，关注的是这段持续时间。

时钟域在这里指采用同一套计时基准和解释规则的时间戳集合。一台机器可以同时有 CPU TSC、多个网卡 PHC，以及具有不同语义的系统时钟；两个进程也可以读取同一台机器上的相同系统时钟。因此，时钟域与机器、进程并非一一对应。

时钟域之间的差异包括起点、计数单位、频率，以及接受的时间校正。两个 API 都以纳秒返回结果，只解决了单位问题；直接相减还取决于其余关系是否兼容。

### 2.2 “精度高”到底指什么

时钟的“精度”可以拆成几个具体指标：

| 指标 | 描述什么 | 不能据此推出什么 |
|---|---|---|
| 表示单位 | 数值按秒、微秒还是纳秒保存 | 使用纳秒字段不代表纳秒准确度 |
| 分辨率 | 能分辨多细的时间变化 | 分辨率小不代表与 UTC 接近 |
| 准确度 | 读数与指定参考的接近程度 | 某一时刻接近，不代表以后仍接近 |
| 稳定性 | 时钟的频率在一定观察时间尺度内变化多大 | 一直稳定地走快，也可能持续偏离参考 |
| 读取开销与抖动 | 读一次时间要多久，耗时波动多大 | 读取变慢不必然意味着时钟走得不稳 |

稳定性与观察尺度有关。微秒级代码片段、持续几分钟的校准、参考源中断后的数小时保持，各自关注不同时间范围内的误差。

### 2.3 UTC、TAI 与闰秒为什么会进入工程问题

UTC 是协调世界时，TAI 是国际原子时。不同时间尺度之间可能存在整秒偏移，闰秒处理方式也有差异。

Linux 的 `CLOCK_REALTIME` 按 Unix/POSIX 时间语义表示日历时间；`CLOCK_TAI` 则由系统时间与内核维护的 TAI 偏移关系构造。`CLOCK_TAI` 的读数来自本机时间和偏移配置，而非直接访问原子钟。[Linux clock_gettime][clock-gettime]

当 PHC 运行在 PTP 时间尺度上、系统日历时间按 UTC 解释时，两者之间几十秒的固定差值可能来自时间尺度，而非同步故障。闰秒平滑处理（leap smear）还会在一段时间内改变时间与标准 UTC 的关系；跨系统比较时，统一的解释规则才能让采用不同策略的读数相互对应。[LinuxPTP phc2sys][phc2sys] [chrony 闰秒处理][chrony-conf]

<a id="sec-3"></a>
## 3. 时间从哪里来

### 3.1 振荡器产生节拍，计数器累计节拍

可以把本地计时拆成两步：振荡器产生周期信号，计数器记录经过了多少个周期。软件再利用频率和一个已知时间点，把计数换算成时间：

$$
t=t_0+\frac{c-c_0}{f}
$$

其中，`c0` 是基准时刻的计数，`t0` 是它对应的时间，`f` 是用于换算的计数频率。换算结果取决于三个因素：`t0` 的准确度、`f` 的稳定性，以及读到的 `c` 对应事件的哪个位置。

石英振荡器利用晶体的机械谐振产生频率参考。温度补偿晶振 TCXO、恒温晶振 OCXO 等设计，通过不同方式减小环境影响。温度、振动和器件老化仍可能改变其频率。[NIST：石英振荡器][nist-quartz]

服务器的 RTC（实时时钟）通常用于掉电后维持日期时间、辅助启动时初始化。程序高频读取系统时间时，使用的是操作系统维护的计时路径。

### 3.2 CPU TSC 与 RDTSC

x86 的 TSC（Time Stamp Counter）是处理器提供的时间戳计数器，`RDTSC` 是读取它的指令。读取结果是计数值，通过相应的换算关系才能把计数差解释成纳秒。

在支持 invariant TSC 的处理器上，TSC 按固定速率推进，不随核心的动态频率状态一起变化。换算时间使用的是 TSC 频率，直接代入当前睿频会算错；TSC 计数差也不代表代码实际消耗的核心执行周期。处理器手册给出了支持位、频率获取方式和指令语义。[Intel SDM][intel-sdm]

invariant TSC 约束的是计数速率。不同核心或 socket 上的计数能否比较、读取指令是否位于预期的测量边界，以及多台服务器的 TSC 是否同步，仍各有自己的验证条件。

### 3.3 网卡 PHC 与交换机时钟

PHC 是 PTP Hardware Clock 的缩写。在支持的 Linux 驱动中，设备时钟可以注册为 `/dev/ptpN`，应用既能读取它，也能通过相关接口获取能力、调整时间或频率。具体哪些功能可用，取决于设备和驱动。[Linux PHC 接口][linux-phc]

网卡在报文经过指定硬件位置时捕获时钟读数，形成硬件时间戳。多端口网卡可以共享 PHC，也可以采用其他时钟布局；设备信息中的时钟布局决定了各端口的读数关系。

交换机同样可以在端口或内部转发路径中记录时间。参与 PTP 同步所需的打点能力，与向观测系统导出普通业务报文时间戳的能力，分别由设备支持；仅凭 PTP 支持信息无法确认后者。

### 3.4 原子钟与卫星授时提供什么

原子钟利用稳定的原子跃迁频率作为参考，通过反馈控制本地振荡器，再由计数构造时间。它仍然涉及振荡、计数和校准，只是参考机制具有更好的长期稳定性。[NIST：原子振荡器][nist-atomic]

交易服务器通常通过授时链路取得参考。一个常见部署是：GNSS（全球卫星导航系统，例如 GPS）接收机提供时间与频率参考，主时钟设备结合本地振荡器生成授时输出，再通过网络把时间分发给服务器。GPS 驯服振荡器会持续调整本地振荡器，使它与接收的参考信号保持一致。[NIST：驯服振荡器][nist-disciplined]

10 MHz 输出主要提供频率参考；1 PPS（每秒一个脉冲）提供秒边界，通常通过另一条信息通道说明脉冲属于哪一秒。日期、时区和时间尺度，则由相应的时间信息与解释规则确定。

## 4. 时钟为什么逐渐不一致

### 4.1 先分清偏移、频率误差和漂移

两只钟在某个时刻相差 5 微秒，描述的是时间偏移。若其中一只每秒多走 1 微秒，描述的是约 1 ppm 的相对频率误差。如果这个快慢差异又随温度或时间变化，才涉及频率漂移。

设参考时间为 `t`，本地读数为 `C(t)`。在较短且运行条件稳定的区间内，可以用下面的模型建立直觉：

$$
C(t)=C(t_0)+(1+y)(t-t_0)+n(t)-n(t_0)
$$

`y` 是相对频率误差，`n(t)` 汇集未被这个简单线性模型描述的变化与观测噪声。若 `y` 恒定，则相对参考的时间偏差以近似线性的方式积累。

例如，假设频率误差为 10 ppm，且完全没有校正：1 秒后积累约 10 微秒偏差，100 秒后约 1 毫秒。文中用于推导的数值均为假设值，用来说明计算关系，不代表硬件实测结果或性能目标。

### 4.2 一次对时为什么不够

把两只钟在某个时刻设成相同读数，只消除了当时的偏移。只要后续推进速度不同，偏差还会重新增长。温度变化、预热、供电与器件老化，又会让频率误差随时间变化。[NIST：漂移与驯服][nist-disciplined]

同步程序通过持续观测偏差、调整时间或频率来维持两只钟的关系。直接把时钟改到另一个值称为跳变校正（step）；逐渐改变推进速度、让偏差慢慢消失称为渐进校正（slew）。具体策略由同步软件和配置决定。

同步后的曲线是振荡器、参考源、网络、采样和控制算法共同作用的结果。本地振荡器自由运行时的表现，则要通过脱离同步控制的实验来观察。

### 4.3 测量噪声也会出现在偏差曲线里

在用户态先读时钟 A，再读时钟 B，两次读取之间存在时间差。系统调用、设备访问或线程抢占都可能扩大这个间隔；网络同步还会受到排队、打点位置和路径不对称的影响。

偏差曲线上出现尖峰时，采样窗口、同步状态和参考源变化可以帮助定位原因。把这些观测与曲线对应起来，可以进一步判断波动来自哪些环节。

## 5. Linux 程序如何读取时间

### 5.1 硬件计数与系统时间之间，还有 timekeeping

Linux 用 clocksource 抽象可用于计时的计数来源。在合适的 x86 平台上，TSC 可以成为 clocksource。内核保存基准计数、基准时间和换算参数，用计数增量构造时间。

常见的整数换算形式可以简化成：

```text
delta_ns ≈ (delta_cycles * mult) >> shift
time_ns  ≈ base_ns + delta_ns
```

这个简化模型展示了换算的主干：`mult`、`shift` 让频率换算主要使用整数乘法和移位。实际实现还会处理计数宽度、溢出、不同时间语义和并发更新。[Linux timekeeping][timekeeping]

系统时间校正会更新相应的软件时间状态和换算关系。通过 PTP 校准 PHC、再校准系统时间时，**改变的是对应时钟及软件换算关系，物理 TSC 并未被设成某个 UTC 数值。**

![时间参考、系统时钟和应用读取路径](assets/hft-04/clock-reading-sync.png)

同步程序负责维持时钟关系，应用则沿读取路径取得打点所需的读数。具体部署可以选择不同的 clocksource 或参考源。

### 5.2 clock_gettime 的重点在 clock ID

`clock_gettime(clockid, &ts)` 的函数名相同，`clockid` 决定读数的语义。常用选择如下：[Linux clock_gettime][clock-gettime]

| 接口或时钟 | 适合的用途 | 主要边界 |
|---|---|---|
| `CLOCK_REALTIME` | 日历时间、带外部时间含义的记录 | 可能发生跳变，也接受频率校正 |
| `CLOCK_MONOTONIC` | 通常的耗时、期限与超时判断 | 不随日历时间的直接跳变而跳变，但接受频率校正；不包含系统挂起时间 |
| `CLOCK_MONOTONIC_RAW` | 观察未受软件频率校正的计时行为 | 保留本地频率误差；RAW 不代表更接近外部参考 |
| `CLOCK_BOOTTIME` | 需要包含系统挂起时间的期限 | 具有与 MONOTONIC 不同的挂起语义 |
| `CLOCK_TAI` | 采用 TAI 语义的时间记录 | 依赖系统时间与 TAI 偏移配置 |
| `CLOCK_THREAD_CPUTIME_ID` | 当前线程消耗的 CPU 时间 | 不是包含排队和等待的真实经过时间 |

两个进程读取同一台主机上的 `CLOCK_MONOTONIC`，通常可以直接关联时间点；两台机器的 `CLOCK_MONOTONIC` 则没有天然共同起点。`clock_getres()` 返回的是分辨率，与参考时钟之间的误差上界还要有另外的校准或测量依据。

在 C++ 层，`std::chrono::steady_clock` 适合表达单调的时间间隔，`system_clock` 用于系统日历时间。具体映射到哪个平台接口属于实现细节，`high_resolution_clock` 是否单调也取决于实现。[C++ 时钟要求][cpp-clocks]

### 5.3 glibc 与 vDSO：一次函数调用未必进入内核

在使用 glibc 的 Linux 程序中，应用通过它调用 `clock_gettime`。当平台、时钟种类和内核实现支持时，glibc 会调用 vDSO（virtual Dynamic Shared Object）。它是内核映射到进程地址空间的小型共享对象，代码在用户态运行。[Linux vDSO][vdso]

在常见的快速读取路径中，vDSO 读取内核提供的时间基准与换算参数，再读取可在用户态访问的计数器，计算当前时间。内核更新参数可能与读取并发发生，因此读取过程会检查序列号；发现数据更新过，就重试，避免拼出由两代参数组成的时间。[Linux vDSO 实现][vdso-source]

走通 vDSO 快速路径时，`clock_gettime` 可以在用户态完成；时钟或配置不支持这条路径时，则可能回退到系统调用。PHC 等设备时钟有自己的读取路径，不能直接套用普通系统时钟的快速读取成本。

这条调用链上，glibc 提供应用接口，vDSO 提供用户态实现路径，内核 timekeeping 管理时间状态，硬件计数器提供计数来源。vDSO 可以使用 TSC，两者位于计时链路的不同层。

### 5.4 直接读 TSC 时，要同时控制测量边界

`RDTSC` 不是完整的串行化指令；`RDTSCP` 也有特定的排序保证与限制。测量代码前后耗时的指令顺序，取决于目标处理器、测量对象和读写要求，同时还受编译器重排影响。[Intel SDM][intel-sdm]

编译器屏障约束编译器重排，CPU fence 约束相应的执行顺序，线程同步则涉及线程间的可见性与顺序。带 `memory` clobber 的内联汇编仍可能允许寄存器计算跨越测量边界，也不保证另一个线程已经看到数据。优化后的机器码能帮助确认测量区间实际包含哪些操作。

热路径可以先把原始计数保存到预分配记录中，将换算、格式化和统计放到后台。对比 `clock_gettime`、C++ 时钟与直接 TSC 的成本时，固定 CPU、编译选项和工作负载，报告耗时分布与采样方式，才能看出平均开销和高分位抖动；时钟稳定性则由专门的实验测量。

### 5.5 读得准与执行得准是两个问题

用单调时钟计算出一个撤单期限，只说明目标时刻如何表示。线程何时醒来、何时获得 CPU、何时完成发单，仍受调度和执行路径影响。

周期任务可以使用绝对期限，避免相对休眠误差逐次累积；实际执行时间仍受调度影响。热路径轮询的时间预算也包含循环工作量、抢占和系统干扰。[Linux clock_nanosleep][clock-nanosleep]

## 6. 网卡和交换机如何给事件打时间戳

### 6.1 打点位置决定了延迟包含什么

应用调用接收函数后再读取时间，得到的是应用已经拿到数据时的读数。报文此前可能已经经过网卡、DMA（直接内存访问）、驱动、内核网络栈和调度等待。使用内核旁路时，路径会变化，但应用打点与硬件接收之间仍然存在一段处理过程。

硬件时间戳把事件捕获位置移到了设备内部，减少了应用调度对事件时间的影响。它究竟对应哪个瞬间，取决于设备在 PHY（物理层）、MAC（介质访问控制层）或其他参考平面的打点位置，以及对报文首部、尾部和固定补偿的定义。

发送方向也一样：应用提交发送请求时，数据可能还在队列里；真正的发送硬件打点发生在后续设备路径中。打点位置改变后，测量覆盖的区间也改变了。

### 6.2 Linux socket 如何交付时间戳

在标准 socket 路径中，应用配置设备与驱动支持的硬件打点能力，并通过 `SO_TIMESTAMPING` 请求相应类型的时间戳。接收时间戳通过 `recvmsg()` 的辅助数据返回；发送时间戳则在稍后通过 `recvmsg(..., MSG_ERRQUEUE)` 读取。[Linux 网络时间戳][timestamping]

这条路径将时间戳与业务 payload 分开交付。专用网卡或 SDK 也有采用报文尾部、描述符或专有元数据格式的实现，交付方式由具体收发接口定义。

Linux 提供时间戳关联 ID 等机制，把发送时间戳对应到原来的发送事件。多个请求同时在途时，返回顺序未必与调用 `send()` 的顺序一致。TCP 还存在字节流与报文边界的差异：一条业务消息可以跨包，一个包也可以包含多条业务消息，因此包与订单的时间戳之间还依赖消息层的对应规则。

### 6.3 支持 PTP，不等于能给所有行情包打点

设备的打点范围可以限于特定 PTP 报文，也可以覆盖更广的接收过滤范围；收发两个方向的能力也可能不同。接口能力与驱动实际接受的配置，共同决定哪些业务包能得到时间戳。

```bash
# 在目标 Linux 主机执行；将 eth0 替换为实际业务网口。
ethtool -T eth0
```

查询结果包含硬件收发时间戳能力、关联的 PHC 编号和接收过滤类型。在此基础上，通过实际收发验证应用能否取得业务包时间戳。[ethtool 手册][ethtool]

使用 DPDK、AF_XDP 或厂商 SDK 时，除了底层网卡支持，还依赖实际数据路径向应用暴露时间戳元数据。

### 6.4 多台交换机不必然带来逐跳时钟比较

如果只测服务器 A 到 B 的单向延迟，参与减法的是 A 的发送时间和 B 的接收时间。中间经过五台交换机，五台交换机的排队与转发耗时会进入总延迟，但不要求应用读取每一台交换机的钟。

只有进一步拆分某一段，例如在 S1 到 S2 的路径上，用 S2 的入端口时间减去 S1 的出端口时间，才需要比较 S1、S2 的时间基准。若只测一台交换机内部的驻留时间，而且入、出打点共享同一计时基准，则可以在本地求差。

<a id="sec-7"></a>
## 7. 多台设备如何同步时钟

### 7.1 同步需要估计偏移，还要处理传输延迟

主时钟发送“现在是某个时刻”时，消息到达接收端已经过去了一段时间。接收端若直接把时钟设成消息中的时间，就会落后一个传输延迟。

NTP（Network Time Protocol）和 PTP（Precision Time Protocol）都通过估计时间偏移与网络延迟来同步时钟。NTP 常用于系统日历时间同步；PTP 则围绕设备时钟、硬件打点和网络设备协作提供同步机制，适合受控网络中的精细同步。最终误差由参考源、打点路径、网络和控制算法共同决定。[NTPv4 RFC][ntp-rfc] [LinuxPTP ptp4l][ptp4l]

### 7.2 用四个时间戳理解 PTP

先看一个简化的端到端延迟测量模型。设主时钟为参考，从时钟相对主时钟的偏移为 `θ`，即“从钟减主钟”。假设一次交换期间 `θ` 近似不变，先忽略打点噪声和中间设备的修正项。

![PTP 四时间戳与双向路径延迟](assets/hft-04/ptp-four-timestamps.png)

四个时间戳分别是：

| 时间戳 | 事件 | 使用的时钟 |
|---|---|---|
| `t1` | 主时钟发送 Sync | 主时钟 |
| `t2` | 从时钟接收 Sync | 从时钟 |
| `t3` | 从时钟发送 Delay_Req | 从时钟 |
| `t4` | 主时钟接收 Delay_Req | 主时钟 |

令主到从的延迟为 `df`，从到主的延迟为 `dr`，则：

$$
t_2-t_1=d_f+\theta,\qquad
t_4-t_3=d_r-\theta
$$

如果往返路径对称，即 `df = dr = d`，就能得到：

$$
\widehat{\theta}=\frac{(t_2-t_1)-(t_4-t_3)}{2},\qquad
\widehat d=\frac{(t_2-t_1)+(t_4-t_3)}{2}
$$

接收端还要取得主时钟侧的时间信息：两步模式中的 `Follow_Up` 可携带精确的 `t1`，`Delay_Resp` 返回 `t4`。实际协议处理会在上述模型基础上，结合 `correctionField` 中的修正值及所采用的延迟机制完成计算。[NIST PTP 测量说明][nist-ptp]

### 7.3 硬件时间戳无法自动消除路径不对称

如果两个方向延迟不同，却仍按对称公式估计偏移，会得到：

$$
\widehat{\theta}-\theta=\frac{d_f-d_r}{2}
$$

例如两个方向的剩余延迟相差 400 ns，偏移估计就会带入 200 ns 偏差。增加采样次数可以帮助分析随机波动，固定的方向偏差则仍会保留。

硬件打点主要减少软件收发路径的不确定性。光纤、链路、设备内部延迟和打点参考位置仍可能带来不对称。LinuxPTP 提供 `delayAsymmetry`、`ingressLatency` 和 `egressLatency` 等配置，用于填写有校准依据的补偿值。[LinuxPTP ptp4l][ptp4l]

### 7.4 交换机中的边界时钟与透明时钟

PTP 网络里常见两种交换机协作方式：

| 类型 | 主要工作 | 对理解误差有什么帮助 |
|---|---|---|
| 边界时钟 BC（Boundary Clock） | 上游端口跟随参考，再用本地时钟向下游发送同步消息 | 把同步分成多段，每一段与本地时钟质量有关 |
| 透明时钟 TC（Transparent Clock） | 转发 PTP 报文，并提供设备驻留时间的修正信息 | 让同步计算能够补偿设备中的部分等待 |

P2P 透明时钟还结合相邻链路的延迟测量。透明时钟测量驻留时间时关心的是时间间隔，不要求它以与边界时钟完全相同的方式维持绝对时间；计时频率的准确性仍然重要。[TI：IEEE 1588 与网络设备][ti-ptp]

这些机制服务于授时报文传播。行情包的逐跳时间戳，则依赖交换机另外提供相应的测量与导出能力。

### 7.5 Linux 上需要明确谁在调整哪只钟

在常见的硬件时间戳部署里，主时钟向网络分发时间，服务器上的 `ptp4l` 同步网卡 PHC，`phc2sys` 再同步 PHC 与系统时钟。同步方向也可以按部署配置反过来，排查时关注的是进程实际在用哪只钟校正哪只钟。

`phc2sys` 还会处理 PTP 时间尺度与系统时间之间的整秒关系。使用自动配置或等待 `ptp4l` 的方式，可以取得相应偏移信息，避免在程序里永久写死秒数。`phc2sys -a` 本身不包含系统时钟，常用配置通过增加 `-r` 将系统时钟纳入同步。[LinuxPTP phc2sys][phc2sys]

如果 `chronyd` 和 `phc2sys` 同时尝试独立控制系统时间，两个控制环就会相互影响。配置服务时画清参考源、被调时钟与同步方向，可以明确每只钟由哪个同步服务负责校正。

<a id="sec-8"></a>
## 8. 如何比较不同时钟域的时间戳

### 8.1 单机内部就可能需要转换

计算“行情到达网卡，到应用取得行情”的延迟时，若 `H0` 来自 PHC、`C0` 来自 TSC，求差就依赖 PHC 与 TSC 之间的换算关系。一台服务器内部也会发生这种跨域转换。

一种常见的局部模型是：

$$
t_{\mathrm{PHC}}\approx a\,(c_{\mathrm{TSC}}-c_0)+b
$$

`a` 是每个 TSC 计数对应的 PHC 时间增量，`b` 是基准计数 `c0` 对应的 PHC 时间。使用相对计数，也有助于避免对巨大绝对值直接做浮点运算。

采集多组对应读数可以估计换算关系，未参与拟合的后续样本则用于检查预测误差。温度、同步控制、跳时或参考源切换都可能使旧参数失效；为映射附上适用时段与版本，才能判断某条记录该使用哪组参数。

### 8.2 两只钟无法同时读取时，先记录读取窗口

最直观的采样方式，是先读参考钟，再读目标钟，再读一次参考钟：

```text
参考读数 r_before → 目标读数 q → 参考读数 r_after
```

在参考时钟连续递增、三次读取按预期顺序执行，且目标读数对应的采样时刻确实落在两次参考读取之间时，可以用：

$$
r_{\mathrm{mid}}=\frac{r_{\mathrm{before}}+r_{\mathrm{after}}}{2},\qquad
w=r_{\mathrm{after}}-r_{\mathrm{before}}
$$

把 `(r_mid, q)` 当作一组近似对应点，同时保留窗口宽度 `w`。窗口越宽，目标读数在参考时间轴上的定位越粗。`w/2` 描述夹取方法的时间定位尺度；参考源准确度、固定访问偏差和相对 UTC 的误差上界，还依赖各自的校准或测量依据。

若设备与驱动支持，`PTP_SYS_OFFSET_EXTENDED`、`PTP_SYS_OFFSET_PRECISE` 等交叉时间戳接口可以帮助建立更紧的 PHC 与系统时间对应关系。前者可提供成组的系统—设备—系统读数，后者依赖驱动和硬件提供更直接的对应能力；目标系统的能力查询结果决定哪种接口可用。[Linux PTP UAPI][ptp-uapi]

### 8.3 两台机器的单向延迟，需要两端可比较

设 A 的发送时间戳误差为 `eA`，B 的接收时间戳误差为 `eB`，真实单向延迟为 `L`，则：

$$
\widehat L=L+e_B-e_A
$$

测得负延迟时，常见原因是时钟关系、时间尺度或事件关联出了问题。两台机器运行 PTP 后，仍要确认打点时钟与同步链路的关系，并评估剩余误差。

测量往返时间时，A 可以用同一只钟记录请求发出和响应返回，在本地完成求差。该区间包含去程、B 的处理与回程，直接除以二会把处理时间与路径不对称一起带入单向网络延迟的估计。

### 8.4 误差预算决定结果是否有用

假设一次跨域延迟测量涉及起点打点、终点打点和映射三个误差项。掌握各项的绝对误差上界后，可以用上界之和作保守预算。分位数、标准差和软件内部估计描述的是其他统计性质，不能当成确定性上界相加。

例如，若映射完成后仍残留 0.1 ppm 的恒定频率误差，那么 1 秒后仅这一项就会新增约 100 ns 偏差。校准间隔越长，这一项误差就越大；实际间隔由初始映射误差、频率误差和运行条件共同决定。

同一只钟上的短区间求差，某些共同偏移可以抵消；跨两只钟的差值未必具有这种性质。误差项之间的相关性会影响最终结果，预算中的独立性假设同样要有依据。

## 9. 时钟稳定性与同步质量的实测

在实际使用的服务器和网络上，时钟关系能保持多久、误差是否满足测量目标，要通过实验回答。下面的 Linux 实验流程配有[只读采样、分析示例](examples/clock_stability/README.md)，用于观测两只钟的相对变化。采样器仅执行读取，时钟设置、频率调整和独立硬件校准由其他工具完成。

### 9.1 先记录环境和被测对象

固定网口、PHC 和 clocksource，并保存环境信息，便于下次复现实验条件：

```bash
uname -a
lscpu
cat /sys/devices/system/clocksource/clocksource0/current_clocksource
cat /sys/devices/system/clocksource/clocksource0/available_clocksource
ethtool -i eth0
ethtool -T eth0
```

将 `eth0` 替换为实际接口。实验记录还包括网卡固件、内核与同步软件版本、PTP profile/domain、主时钟身份、网络拓扑、同步方向和负载。测试温度影响时，实际温度时间序列才能支持温度与偏差之间的分析；“空闲”和“繁忙”只描述负载状态。

`current_clocksource` 为 `tsc`、网卡暴露 `/dev/ptp0` 等查询结果，说明的是计时来源与设备接口。稳定性结果来自后续的连续观测。

### 9.2 选择参考钟，决定实验能证明什么

比较两只钟时，观察值同时包含双方误差和读取路径的影响。参考钟有独立的质量依据时，才能据此评价被测钟的准确度；缺少这一依据时，实验结论限于两者的相对变化。

| 比较对象 | 适合观察什么 | 主要限制 |
|---|---|---|
| `REALTIME` 与 `MONOTONIC_RAW` | 系统校正后的时间相对原始计时的变化 | 两者可能来自同一 clocksource，不能独立验证振荡器的外部准确度 |
| PHC 与系统时间 | 当前同步链路下，两者的相对偏差和转换质量 | 若系统时间正由该 PHC 校准，双方误差可能相关 |
| 自由运行设备钟与外部参考 | 本地频率误差、预热与长期漂移 | 参考源和比较仪器也需要校准 |
| 两台机器的 PPS 输出与独立测量设备 | 秒边界的相对偏差、同步与保持表现 | PPS 路径、线缆和仪器延迟要纳入测量 |

两台服务器相对公共参考的误差范围，由独立于被测同步环的观测来验证。控制环即使把自身的 offset 估计调得很小，也可能保留未建模的固定路径偏差。[NIST 频率稳定性分析][nist-stability]

### 9.3 先看同步状态，再采集连续读数

对已经运行的服务，先查询其状态。chrony 与 LinuxPTP 的查询示例如下，按实际部署选用：

```bash
chronyc tracking
chronyc sources -v

pmc -u -b 0 'GET TIME_STATUS_NP'
pmc -u -b 0 'GET PORT_DATA_SET'

# 使用 systemd 且服务名称如下时，保存同步状态变化。
journalctl -u ptp4l -u phc2sys --since '-30 min'
```

`pmc` 的管理 socket 和 domain 等参数与实际部署一致时，才能查询到对应服务；查询权限和服务名也按环境调整。输出中的主时钟身份、端口状态、偏移估计、频率校正和失锁信息，有助于解释后续采样。chrony 的 `tracking` 包含本机与参考的估计关系，PTP 状态中的 offset 也属于协议与控制环的观测结果。[chronyc 手册][chronyc] [pmc 手册][pmc]

观测实验沿用现有同步服务，只读取状态和时间；另起一个进程调整同一只钟，会改变原本要观察的同步行为。

### 9.4 用随文程序采集时钟对

在仓库根目录进入示例目录：

```bash
cd hft/examples/clock_stability

# 约 10 分钟，观察系统校正后的时间相对 RAW 如何变化。
python3 collect.py --target realtime --reference raw \
  --interval 0.1 --count 6001 --output realtime_vs_raw.csv

python3 analyze.py realtime_vs_raw.csv \
  --series realtime_vs_raw_series.csv
```

如果已经确认 PHC 编号，并且 PHC 与系统 TAI 时间的尺度配置正确，可以比较：

```bash
python3 collect.py --target /dev/ptp0 --reference tai \
  --interval 0.1 --count 6001 --output phc_vs_tai.csv

python3 analyze.py phc_vs_tai.csv --series phc_vs_tai_series.csv
```

采样器运行在 Linux 上，使用 Python 3.8+ 标准库，读取 PHC 需要设备权限。它按“参考—目标—参考”的顺序采样，保留三个原始整数纳秒读数、读取窗口宽度，以及计划和实际采样开始时间。调度使用单调时钟；采样落后时跳过已经错过的时隙，避免后续样本挤在一起。

为减少逐次格式化和文件写入对观测的影响，样本先留在内存，结束后统一写 CSV。内存占用会随样本数增长，因此它适合有界实验；进程被强制终止或机器故障时，未写出的样本会丢失。程序要求输出路径尚无文件，以免覆盖之前的实验。

这个程序用于研究读数关系，其时间开销包含 Python 调用、系统接口和可能的设备访问，无法用来隔离单条 `RDTSC` 指令的性能。

示例已通过合成数据的分析与命令行测试；Linux 采样及真实 PHC 尚未实机验证，目前没有由该程序产生的硬件稳定性结果。

### 9.5 从偏差曲线看频率，再看残差

对第 `i` 个样本，令参考中点为 `ri`，目标读数为 `qi`，相对偏差为：

$$
o_i=q_i-r_i
$$

观察 `oi - o0` 随实际经过时间的变化：近似线性的斜率反映这个窗口内的平均相对频率差；突然跳变则要结合同步日志，查找跳时、参考源切换、读数异常或时间尺度变化。

分析器用相对时间拟合：

$$
x_i=\frac{r_i-r_0}{10^9},\qquad
y_i=o_i-o_0\approx\alpha+\beta x_i
$$

这里 `xi` 用秒，`yi` 用纳秒，`β` 的单位就是 ns/s，因此：

$$
\text{相对频率差（ppm）}=\frac{\beta}{1000}
$$

正值表示目标钟相对参考钟走得更快。先以整数减去起点，再转换为浮点数，可以避免把约 `10^18` 量级的 Unix 时间纳秒值直接用于浮点拟合，丢失细小差值。

至少同时查看三个序列：

1. **偏差变化随时间**：保留长期趋势和跳变。
2. **去掉常数与线性趋势后的残差**：观察这个窗口内剩余的波动。
3. **读取窗口宽度随时间**：检查异常样本是否伴随调度或访问路径变慢。

小残差说明线性模型较好地解释了这些观测点；判断时间准确度和振荡器自身的稳定性，还依赖独立参考与实验条件。若窗口内发生了状态切换，分段拟合有助于呈现各阶段的频率变化，避免单个 ppm 数值掩盖差异。

如果希望按读取窗口宽度筛选样本，可以显式设置阈值：

```bash
# 10000 ns 只是命令示例，应按实际读取分布和实验目标选择。
python3 analyze.py phc_vs_tai.csv --max-bracket-ns 10000 \
  --series phc_vs_tai_filtered_series.csv
```

分析器报告过滤前后的样本数量与窗口分布，原始文件保持不变。剔除比例与筛选后的曲线一起呈现，才能看出平滑结果排除了多少观测。程序会识别直接可见的反向读数，并停止对这类记录做全窗口拟合；向前跳时与同步状态检测尚不完整，这部分由原始曲线和日志辅助判断。

### 9.6 把锁定、自由运行和失锁保持分开测

空闲十分钟的观测只覆盖一种运行条件。面向实际部署的稳定性实验还包括以下状态：

| 实验阶段 | 保持或改变什么 | 关注的结果 |
|---|---|---|
| 预热阶段 | 从启动到温度与同步状态趋稳 | 频率、偏差和锁定过程怎样变化 |
| 已同步的稳定阶段 | 固定参考、拓扑和主要负载 | 相对偏差分布、频率校正与偶发尖峰 |
| 负载变化 | 保持参考关系，改变计算或网络负载 | 读取抖动、排队、温度与偏差是否一起变化 |
| 自由运行 | 本地钟不接受外部校正，保留独立参考观测 | 本地相对频率误差及随时间的变化 |
| 失锁保持与恢复 | 在测试环境中中断、恢复授时来源 | 误差增长、可用保持时间、重锁期间是否跳时 |

同步状态变更安排在独立测试环境中，先确定被调时钟，再通过相应工具执行，随文采样器仅负责观测。自由运行、失锁保持和正常同步分别记录和分析：失锁后，软件可能继续使用此前估计的频率校正，因此失锁保持的表现会受同步历史影响。

单独分析恢复阶段，可以更清楚地观察重新锁定的过程。若把主钟切换前后的读数合成一个分布，偏移变化就可能被掩盖，控制过程也容易被误当成平稳噪声。

### 9.7 什么时候需要 Allan 偏差

偏差曲线和局部频率已经能解释很多工程问题。如果还要比较不同平均时间尺度上的频率稳定性，可以进一步使用 Allan deviation（Allan 偏差）。

设有 `M` 个连续、无缺口、长度均为 `τ` 的区间，每个区间的平均相对频率偏差为 `ȳi`。这里 `ȳi` 是无量纲数，若原始数据用 ppm 表示，需要先乘以 `10^-6`。一个常用估计形式为：

$$
\sigma_y(\tau)=
\sqrt{\frac{1}{2(M-1)}\sum_{i=1}^{M-1}
(\bar y_{i+1}-\bar y_i)^2}
$$

它比较相邻区间的平均频率变化，并随 `τ` 给出不同的观察尺度。恒定频率偏差在相邻差分中会抵消，因此 Allan 偏差衡量的是频率稳定性；频率校准是否正确、绝对时间是否接近 UTC，依赖另外的测量。[NIST 频率稳定性分析][nist-stability]

随文采样可能出现调度迟到或跳过时隙，名义上的 `0.1 s` 只有在实际间隔满足条件时，才能用于等间隔公式。缺测、死区、跳时和长周期样本不足也各有处理要求。示例分析器只提供相对偏差和线性拟合，未实现 Allan 偏差计算。

### 9.8 最终报告应给出怎样的结论

一份可用于交易系统决策的报告，会把实验条件与结论一起呈现：使用哪只参考钟，测了哪个时钟对，在什么温度、负载和同步状态下，观察了多长时间，保留和剔除了多少样本。

测量结果分别包括偏差变化、平均相对频率差、残差、读取窗口和状态转换。缺少独立参考时，结论限于相对关系；数据来自同步软件内部估计时，则注明控制环观测口径。有限样本的最大值只能描述本次观测，不能充当未来的误差上界。

如果要分辨的交易延迟变化与当前时间不确定度处在同一量级，就优先改善授时、打点或跨域转换。这种情况下，延迟图上的波动可能混有时钟误差，难以可靠归因于交易程序。

## 10. 把时钟用于交易系统

### 10.1 把完整延迟拆回同一条事件记录

用 `H0、C0、C4、H1` 拆解一次本机延迟。假设收发打点共用 PHC，CPU 读数已通过有效映射转换到该 PHC 时间轴，且这次测量没有跨越跳时或映射切换边界。

下面是一组用于说明计算关系的假设数值：

| 区间 | 时间差 | 本例覆盖的工作 |
|---|---:|---|
| `C0 - H0` | 120 ns | 网卡接收打点到应用取得行情 |
| `C4 - C0` | 450 ns | 解码、订单簿、策略、风控与编码 |
| `H1 - C4` | 180 ns | 订单就绪到网卡发送打点 |
| `H1 - H0` | 750 ns | 本机这次行情到订单的总区间 |

这里各段边界连续、对应同一次事件，且采用可比较的时间基准，因此可以相加得到总区间。

实际记录通过事件 ID、原始时间戳、时钟来源和映射版本保留这种对应关系。多对一的策略输入、批量发单或一个报文包含多条消息时，由事先定义的归因规则确定哪条行情与哪笔订单配对。

统计时先按事件计算总耗时，再求总耗时的分位数。各段的 p99 通常不是同一批事件，不能把它们相加当成总 p99。

### 10.2 让时间质量随事件一起进入观测系统

只保存一个 `timestamp_ns`，离线分析时很难知道它是 TSC 换算值、PHC 读数还是系统日历时间。记录格式关联以下信息后，读数才有完整的解释依据：

| 信息 | 用途 |
|---|---|
| 事件或消息 ID、必要的协议序列号 | 对应同一条业务路径，而不是只按时间排序 |
| 打点位置与原始时间戳 | 明确事件边界，允许重新换算 |
| 时钟来源与时间尺度 | 区分设备、clock ID、UTC/TAI 等语义 |
| 映射或校准版本 | 找到本条记录使用的换算关系与适用时段 |
| 同步状态、主时钟身份和参考健康状态 | 解释切换、失锁和时间质量变化 |
| 可获得的误差估计及其口径 | 区分测得分布、控制环估计和校准上界 |

热路径可以保存紧凑的 ID，在后台关联配置与校准元数据，减少重复的字符串记录。诊断队列满时，按既定策略丢弃观测样本并累计数量，可以避免测量系统反过来阻塞交易路径。

两个事件的时间差小于时间不确定度时，仅凭时间戳无法可靠判定先后。行情去重、缺口恢复和会话顺序，依赖协议提供的序号、标识与规则。

### 10.3 时间关系失效时，要知道哪些计算仍然可用

跨机同步失效后，本机单调时钟上的短区间测量可能仍然可用；依赖公共时间的行情新鲜度判断与跨机单向延迟，则可能已经失去依据。故障处理按受影响的功能分别进行：

| 变化 | 需要重新检查什么 |
|---|---|
| 主时钟或时间尺度变化 | 绝对时间关系、整秒偏移、跨机比较 |
| PHC 跳时或重新初始化 | 跨越该点的区间、PHC 与 TSC 的旧映射 |
| CPU、内核或虚拟化环境变化 | TSC 可用性、跨核一致性、实际读取路径 |
| 失锁时间持续增长 | 保持期间的误差预算是否仍满足业务要求 |
| 时间戳缺失、返回延迟或关联失败 | 样本是否完整，是否把错误事件配成了一对 |

交易决策中的降级规则提前定义。例如，依赖交易所时间判断行情年龄的功能，在时间质量不足时按规则降级或停止；仅用于后台性能图的跨机样本，可以先标为不可比较，并保留原始数据供排查。

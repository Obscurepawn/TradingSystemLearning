# 高性能订单簿与撮合引擎的实现与优化

从价格索引、订单布局到单写者撮合

**OrderBook（订单簿）记录一个交易品种中等待成交的买卖订单，包括价格、剩余数量和排队顺序。Matching Engine（撮合引擎）处理新订单、撤单和改单，按交易规则撮合成交、更新订单簿，并返回处理结果。**

## 1　订单簿与撮合引擎的接口语义

以普通价格时间优先的连续竞价为例，订单簿有买侧 bid 和卖侧 ask。买价从高到低、卖价从低到高排列，同价订单按时间优先级排队；每单保存标识、方向、价格、剩余数量和优先级序号。最高买价与最低卖价组成 BBO（best bid and offer），L2 深度按价位汇总数量，逐订单视图则保留同价位内的订单和顺序。隐藏订单及其他优先级规则会扩展这个基础模型。

**订单簿库提供查找、插入、删除和查询盘口等操作。** 以下用示意性的函数名说明这些操作。有的库也把撮合逻辑放在 `OrderBook::add()` 中，阅读实现时要看清这个函数究竟做了哪些事。

| 概念接口 | 语义 | 对数据结构的要求 |
|---|---|---|
| `find(order_ref)` | 定位一张仍有效的订单；标识包含其唯一域 | 从外部 ID 找到稳定节点或 handle |
| `insert_resting(order)` | 把订单加入对应价位的队列 | 找到价位，维护排队顺序和该价位的总挂单量 |
| `reduce(handle, delta_qty)` / `erase(handle)` | 减少剩余量或移除节点，并更新价位统计 | 快速定位节点、删除末单后维护非空档 |
| `best(side)` / `next_level(side, price)` | 返回该侧最优或后续非空价格层 | 有序价格索引与最优价维护 |
| `depth(n)` / `snapshot()` | 读取前 n 档行情，或生成盘口快照 | 快照中各字段对应同一处理进度，并注明序号 |

新订单到达时，撮合引擎先检查它能否与对侧挂单成交。能成交就逐笔处理；还有剩余数量、且允许继续挂单时，才调用 `insert_resting()` 加入订单簿。行情重建中的 `apply(exchange_event)` 则根据交易所发来的事件更新本地盘口，例如增加订单、撤销订单或扣减成交数量。

**交易参与者向撮合引擎提交新单、撤单等命令，再接收处理结果。** 下表列出常见接口及其含义；具体支持哪些命令、哪些时段可以使用，以交易所协议和规则为准。

| 命令或查询 | 主要输入 | 处理语义 |
|---|---|---|
| `NewOrder` | 请求标识、客户订单号、账户、品种、方向、类型、数量、可选限价、TIF 等 | 检查申报是否合法，按规则撮合，再按订单类型处理未成交的余量 |
| `Cancel` | 请求标识、目标订单标识，必要时含数量参数 | 处理到该命令时撤销允许撤销的剩余量；已经成交的部分保留 |
| `Amend` / `Replace` | 目标订单、新价格、新数量，必要时含新的订单标识 | 修改价格或数量；明确能否保留原来的排队位置，以及修改失败时原单是否保留 |
| `MassCancel` | 账户、会话、品种或订单组等筛选条件 | 撤销处理请求时符合条件的订单，并报告处理结果 |
| `QueryOrder` / `BookSnapshot` | 有权限查看的订单或盘口范围，可选观察序号 | 返回订单或盘口状态，并注明已处理到的序号；可由独立查询服务提供 |

限价是买单愿意支付的最高价，或卖单愿意接受的最低价。TIF（time in force）说明订单是否需要立即成交，以及未成交的部分可以等待多久：

- **DAY**：未成交的部分可以在当日有效期内继续挂单，到规定时点失效。
- **GTC**：未成交的部分持续挂单，直到成交、撤销，或满足市场规定的其他终止条件。
- **IOC**：立即成交能够成交的部分，剩余部分取消。
- **FOK**：必须立即全部成交，否则整单不成交。

市价单能扫哪些价位、是否有价格保护、余量如何处理，也取决于市场规则。A 股实现要使用对应品种、对应交易阶段支持的申报类型，不能直接把以上选项全部开放。

一条命令可以产生多条回报：`Accepted` 表示新单已接受，`Rejected` 表示拒绝，`Execution` 记录成交价格和数量，`Canceled`、`Replaced`、`Expired` 分别报告撤销、替换和到期。订单被接受后，可能立即全部成交，也可能还有余量继续挂单，具体看成交回报与剩余数量。同步库可以在 `process(command, event_sink)` 中输出这些事件；异步网关返回“成功入队”时，则只是把命令放进了待处理队列。回报中保留关联订单或请求的标识，事件 ID 用于重放时识别重复回报。统计吞吐量时，一笔成交和发给买卖双方的两份回报也要分别计数。

撤单与撮合按引擎确定的顺序竞争：客户发出撤单后，到引擎处理前，原单仍可能被别的命令成交。改单还要写清数量参数表示“新的总委托量”“新的剩余量”还是“减少多少”。例如 Nasdaq OUCH 的 Replace 会重置时间优先级；其 Cancel 数量字段表示新的最大累计成交数量，零表示撤销全部余量，多余的撤单还可以被静默忽略。把这些动作统一包装成 `cancel(id, qty) -> bool`，会丢失数量与处理结果的含义。[Nasdaq OUCH 5.0，2.2—2.4 节](https://www.nasdaqtrader.com/content/technicalsupport/specifications/TradingProducts/OUCH5.0.pdf)。

考虑一个仅含普通显示限价单的盘口，采用价格时间优先、以被动订单价格成交：

| 卖侧价格 | 该价位从队头到队尾的订单 |
|---:|---|
| 10.01 | A：100 股；B：200 股，B 晚于 A |
| 10.02 | C：100 股 |

此时提交 D：买入 250 股，限价 10.02。引擎先让 D 与 A 在 10.01 成交 100 股，再与 B 在 10.01 成交 150 股。D 全部成交，A 移出订单簿，B 剩余 50 股且保留原有队列位置，C 仍为 100 股。若随后成功撤销 B，撤掉的是剩余 50 股。这条命令产生两笔成交，涉及价格选择、FIFO、减量、节点删除和结果输出，因此命令数量与成交数量要分别计数。被动价格成交机制可参见 [Coinbase 的 Price Improvement 说明](https://docs.cdp.coinbase.com/exchange/concepts/matching-engine)，其他分配规则另行适配。

查询接口还要说明：返回的是处理到哪一条命令时的状态。例如快照中的 `applied_seq = 1200` 表示该分片已经处理完前 1200 条输入。查询副本可能比撮合线程慢；若要查到刚提交的命令产生的结果，就等副本处理到那条命令，再读取快照。快照中的价格、数量等字段应对应同一个处理进度。公开行情只展示规定的盘口信息，客户回报包含自己的订单信息，引擎内部则维护完整订单簿。跨分片查询还要说明，各分片的结果分别更新到了哪个序号。

## 2　用价格数组代替树查找

插入挂单、更新某档数量或查询深度时，都要按价格找到对应价位。最直接的实现是 `map<Price, Level>`，每个价格对应一条订单队列。假设有 M 个非空价位，树查找花费 O(log M) 次比较；在节点分散的实现中，比较还伴随着沿指针逐层访问内存。价格相同的订单很多时，这条路径会被反复执行。

A 股的价格规则给出了另一种做法。以前收盘价 10 元、常规涨跌幅限制 ±10% 的主板股票为例，当日价格范围是 9—11 元，tick 为 0.01 元，一共只有 201 个价位。直接为这 201 档分配数组，价格转换成整数分后，10.01 元对应的下标就是 `1001 - 900 = 101`。原来的树查找变成一次减法和一次数组访问。

```text
price_tick = 已按 tick 换算的整数价格
index      = price_tick - lower_tick
level_count = upper_tick - lower_tick + 1
```

这里采用的是当日静态涨跌停边界。沪深 2026 年 7 月 6 日生效的规则下，主板普通股票及主板风险警示股票的常规涨跌幅均为 ±10%，科创板和创业板为 ±20%；北交所股票常规为 ±30%。这些股票的 tick 均为 0.01 元。沪深新股上市前五个交易日、北交所公开发行上市首日等无日涨跌幅限制的情形，要使用另外的价格存储方案。基金等品种也有不同精度，tick 按品种配置。[上交所交易规则](https://www.sse.com.cn/lawandrules/sselawsrules2025/trade/universal/c/c_20260424_10816492.shtml)、[深交所交易规则](https://docs.static.szse.cn/www/lawrules/rule/trade/current/W020260424690713155663.pdf)、[北交所交易规则](https://www.bse.cn/jygl_list/200028217.html)。

如果每侧每档保存队头、队尾、总量和订单数等字段，共占 32 B，双侧价位数组的内存就是 `2 × level_count × 32 B`：

| 参考价格与涨跌幅 | 每侧价位数 | 双侧价位数组 |
|---|---:|---:|
| 10 元，±10% | 201 | 12.56 KiB |
| 100 元，±10% | 2,001 | 125.06 KiB |
| 1,000 元，±10% | 20,001 | 1.221 MiB |
| 100 元，±20% | 4,001 | 250.06 KiB |
| 100 元，±30% | 6,001 | 375.06 KiB |

数组为每个合法价位保留一个位置，包括没有挂单的空档。这个空间代价换掉了查找路径上的比较和指针访问。`std::vector<Level>`、定长数组或预分配 arena 都可以实现这种布局；使用 vector 时，开盘前创建好全部元素，盘中只访问已有位置。`reserve()` 只预留容量，按下标使用前还要建立相应的 size。

这种做法在公开实现中有直接例子：QuantCup 冠军代码按价格索引 `pricePoints`；SimpleOrderbook 则用 `vector<level>` 保存价位，各价位再挂订单链。两者都利用了已知价格网格，连续存储的是价位表，订单节点另行组织。[QuantCup 原始代码](https://www.ermolinskiy.net/engine.c)、[SimpleOrderbook 的价位结构](https://github.com/jeog/SimpleOrderbook/blob/3411cebb9756b80fd2cb3b442cfb109ca853068b/include/simpleorderbook.hpp#L506)。

工程上直接读取当日证券参考数据中的涨停价和跌停价，比临时用浮点数乘百分比稳妥。自行计算时，取整、除权除息参考价及不足一 tick 的特殊处理都按交易所规则执行。转数组下标前先检查价格范围和 tick 对齐，再做整数减法。这样，报价合法性和数组边界使用同一套定义。

## 3　用位图跳过空价位

数组解决了“这个价格在哪里”，但最优卖价被吃完后，还要找到下一个有挂单的卖价。如果从当前位置逐档向上扫描，跨过的空档越多，耗时越长。一个有两万个位置的数组，只挂了几十档订单时，这个问题尤其明显。

QuantCup 的实现就采用线性扫档。作者在注释中说明，比赛数据多数只检查一两档，最多不超过五档，因此简单循环很有效。换成最优价之间相隔数百 tick 的订单流，同一段代码就要做更多检查；它的表现与输入价格分布密切相关。[QuantCup 扫档实现](https://www.ermolinskiy.net/engine.c)。

可以给每侧数组增加一张位图：第 i 位为 1，表示第 i 个价位有订单。连续 64 个价位的状态装进一个 `uint64_t`，查找时一次排除 64 个空档。搜索起点 `start` 使用非负整数；如果 `start >= N`，直接返回没有后续价位。否则从该位置向后寻找卖价，先检查它所在的机器字：

```cpp
const auto word = start / 64;
const auto bit = start % 64;
const std::uint64_t candidates =
    nonempty[word] & (~std::uint64_t{0} << bit);

if (candidates != 0) {
    return word * 64 + std::countr_zero(candidates);
}
// 当前机器字里没有符合条件的价位，再找后面的非零机器字。
```

如果后面还有很长一段零机器字，就再加一层摘要：上层每一位表示下层一个机器字是否非零。依次向上建立摘要，找到非零区域后再向下定位，就得到分层位图。一般搜索成本为 O(log₆₄ N)，N 是价格槽数；固定价格范围下，实际层数很少。卖侧找最小置位，买侧找最大置位。

最优价本身仍然缓存下来。新订单建立更优档位时直接更新 best；只有当前最优档被清空，才通过位图寻找下一档。一个价位从零张订单变成一张，或从一张变成零张时，更新对应 bit 及必要的上层摘要；同档内普通的加单、减量不会改变它是否为空。

双侧基础位图只需 `2 × ceil(N / 64) × 8` B。N 为 20,001 时，基础位图共 5,008 B，摘要层另外占用少量空间，远小于价位数组。实现中把最后一个机器字的无效位保持为零，并先判断候选字是否为空：C++20 的 `std::countr_zero(0)` 返回位宽，这个结果不是有效的价位下标。

## 4　为稀疏价格域分配存储

把一只 10 元股票的价位表扩展到全市场，空间问题就出现了。仅按“5000 个品种、每个参考价 100 元、±10%”这个容量算例，两侧价位数组就约占 611 MiB，还没算订单和 ID 索引。高价、细 tick、长期不设固定日价格边界的品种，空档占用会更大。

一种折中是分块数组。例如每块覆盖 256 个 tick，块内仍然直接寻址并维护位图，只为实际用到的块准备存储。块之间用有序目录连接；某块清空后，从目录找到下一个非空块，再在块内定位价格。定位不再是单次数组访问，但空间主要花在活跃价格附近。预先准备可复用的块，还能把第一次进入新价格区域时的内存分配移出撮合过程。

这个目录可以用树，也可以用多层稀疏索引。若一个品种活跃价位很少，直接用有序树保存非空价位也很合理。B-tree 在一个节点里保存多个键，减少树高和节点间跳转；代价是插删时会移动元素。订单因此保存稳定的 `LevelId`，树内保存“价格 → LevelId”，就不必让订单指向会搬移的树内对象。[Abseil B-tree 设计说明](https://abseil.io/about/design/btree)。

使用树也不意味着每撮合一单都要重新查树。价格索引负责找到位置，已经排好序的链负责向后推进。exchange-core 就用 ART 索引价位，同时维护订单链和最优订单指针；扫单沿链前进，只有价位创建、删除等操作才涉及相应的索引维护。[OrderBookDirectImpl](https://github.com/exchange-core/exchange-core/blob/2f8548749839e9095c8dc597e4b61521d259fa5d/src/main/java/exchange/core2/core/orderbook/OrderBookDirectImpl.java#L43)。

| 价格组织方式 | 主要省掉的工作 | 主要付出的代价 |
|---|---|---|
| 连续数组＋位图 | 按价格查树、逐个扫描空档 | 为整个价格范围分配价位槽 |
| 分块数组＋有序目录 | 为大片空价格区间保存完整价位对象 | 查询块目录、维护新块和空块 |
| B-tree / ART 等稀疏索引 | 保存所有可能价格的位置 | 索引路径上的访问与结构更新 |
| 排序 vector | 节点分配和分散的指针访问 | 新建、删除价位时移动后续元素 |

这里的树还要看具体代码怎样维护元数据。例如 brprojects 的 AVL 实现会递归遍历子树求高度，再计算平衡因子。把高度保存在节点中、沿更新路径维护，才能避免反复遍历整片子树。项目里某次再平衡的耗时，包含了这种实现选择。[递归求高度的代码](https://github.com/brprojects/Limit-Order-Book/blob/af6e5349874649fe196bd6c26653d357f5a751f2/Limit_Order_Book/Book.cpp#L288)。

价格网格也未必处处相同。港股按价格区间使用不同 tick，可以先把合法价格映射成有序的档位编号，再做数组或块索引；加密资产的报价和数量精度则从产品配置读取。通用价格类型保留符号，才能容纳允许零价或负价的期货合约。固定 tick 的 A 股路径可以专门实现，其他市场保留各自的映射逻辑。[HKEX 价差表](https://www.hkex.com.hk/Services/Trading/Securities/Overview/Trading-Mechanism/Reduction-of-Minimum-Spreads?sc_lang=en)、[Coinbase 产品字段](https://docs.cdp.coinbase.com/api-reference/exchange-api/rest-api/products/get-single-product)、[CME 负价格支持](https://www.cmegroup.com/notices/clearing/2020/04/Chadv20-160.html)。

## 5　通过订单 ID 直接定位撤单节点

价格能直接定位之后，撤单仍有另一条查找路径：客户给的是订单号，不是队列中的位置。假设涨停价排着十万张买单，撤掉其中一张时，从队头逐个比较 ID，即使价位查找只花常数时间，撤单仍会随队列变长而变慢。

因此 ID 索引要一直指向可直接操作的订单节点。只找到一个订单对象，再让底层容器搜索一次，仍然会重复付出查找成本。Liquibook 默认撤单路径就是一个具体例子：按价格 `find()` 后，继续逐个比较同价位订单；查找成本可达 O(log Nₒ + Qₚ)，其中 Nₒ 是订单数，Qₚ 是该价位队列长度。[同价位查找代码](https://github.com/enewhuis/liquibook/blob/2427613b32f1667abae68a01df6af9ba8270f8e7/src/book/order_book.h#L642)。

让索引返回稳定的 handle，并在订单节点中保存 `prev`、`next`，撤销中间订单只需连接它的前后两个邻居：

```text
handle = order_index.find(order_id)
node   = pool[handle.slot]
检查 handle.generation 与 node.generation 是否一致

如果有前驱：前驱.next = node.next；否则更新该价位的 head
如果有后继：后继.prev = node.prev；否则更新该价位的 tail
扣减该价位的总量与订单数
删除 ID 映射，回收节点
```

已知有效 handle 后，双向链表摘除节点是 O(1)。如果这是该价位最后一张订单，还要清除位图，必要时更新 best；这些工作与节点摘除分开计算。用同一张 ID 索引处理撤单、改单和订单查询，也能避免各入口再维护一套不同的定位方式。

还可以更激进：撤单时只把数量置零，保留节点，撮合遍历遇到它时跳过。QuantCup 使用的就是这种懒删除，撤单路径只剩很少的写操作。代价是被撤订单继续占用空间，之后的主动单要穿过这些墓碑。撤单风暴发生在长队列中时，清理成本会集中到后面的撮合命令上。冠军原始实现还采用固定容量、单调分配且不回收的 arena，适合有界比赛输入；持续运行的服务则要设计回收。原文件保留了 `All Rights Reserved` 声明，可阅读其思路，直接复用另行核对许可。[QuantCup 撤单与节点管理](https://www.ermolinskiy.net/engine.c)。

ID 索引本身也有空间：若引擎内部生成连续编号，可以直接用编号访问数组；若面对客户提供的稀疏 ID，则用预分配哈希或分页映射。严格递增并不保证连续，例如 OUCH 的编号规则允许缺口，也有各自的唯一域。映射键还要包含所需的账户、会话或交易日信息。[OUCH 5.0 数据类型](https://www.nasdaqtrader.com/content/technicalsupport/specifications/TradingProducts/OUCH5.0.pdf)。

开放寻址哈希把键和值放得更紧凑，有助于减少查找时的指针跳转；代价是高负载或大量删除后，探测链可能变长。容量在接单前预留，扩容和整理安排在受控时机，才能避免一次撤单触发整表搬迁。[Swiss Tables 设计](https://abseil.io/about/design/swisstables)。

## 6　预分配订单池并压缩热数据

定位和摘链都变快后，新订单到达时 `new`、订单结束时 `delete` 的成本就更显眼了。订单在不同位置分配，撮合沿队列前进时还会不断访问分散的内存。可以预先分配一批节点，空闲槽位放进 free list；新单取一个槽位，订单结束后再放回去。exchange-core 对订单和价位 bucket 都做了池化，分配与回收沿同一套路径处理。[取得订单对象](https://github.com/exchange-core/exchange-core/blob/2f8548749839e9095c8dc597e4b61521d259fa5d/src/main/java/exchange/core2/core/orderbook/OrderBookDirectImpl.java#L146)、[回收订单与价位](https://github.com/exchange-core/exchange-core/blob/2f8548749839e9095c8dc597e4b61521d259fa5d/src/main/java/exchange/core2/core/orderbook/OrderBookDirectImpl.java#L339)。

C++ 中可以把节点放进连续池，用 32 位槽位索引代替部分 64 位指针。下面给出一份 32 B 价位、64 B 订单的布局，便于计算容量和检查字段：

```cpp
using Tick = std::int64_t;
using Qty = std::uint64_t;
using Index = std::uint32_t;
constexpr Index nil = UINT32_MAX;

struct Handle {
    Index slot;
    std::uint32_t generation;
};

struct Level {
    Index head = nil;
    Index tail = nil;
    Qty total_qty = 0;
    std::uint32_t order_count = 0;
    std::uint32_t flags = 0;
    std::uint64_t reserved = 0;
};

struct OrderHot {
    std::uint64_t internal_id;
    std::uint64_t priority_seq;
    Tick price;
    Qty leaves_qty;
    Index prev, next;
    std::uint32_t generation;
    std::uint32_t level_index;
    std::uint32_t instrument_id;
    std::uint32_t owner_ref;
    std::uint16_t flags;
    std::uint8_t side, state;
    std::uint32_t reserved;
};
static_assert(sizeof(Level) == 32);
static_assert(sizeof(OrderHot) == 64);
```

撮合频繁读取价格、剩余量、链表索引和少量控制字段；客户字符串标识、审计说明等放到另一份冷数据中，通过编号关联。这样扫单时加载的内存更少。在缓存行大小为 64 B 的目标机器上，如果希望一个 64 B 节点恰好占一行，池的首地址还要按缓存行对齐。单纯把结构体凑成 64 B，不会自动获得这个效果。

![连续价位数组、非空位图、外部订单 ID 索引与池内双向 FIFO](https://raw.githubusercontent.com/Obscurepawn/TradingSystemLearning/main/hft/assets/orderbook-matching-engine/dense-ladder-order-pool.png)

节点池与价格索引可以独立选择。连续池里的节点既能组成 FIFO，也能组成树；OpenBook 的 crit-bit tree 就放在 slab 中，以整数句柄连接节点，并维护空闲链。它连续保存的是实际节点，不是所有可能的价格。[OpenBook slab](https://github.com/openbook-dex/program/blob/c85e56deeaead43abbc33b7301058838b9c5136d/dex/src/critbit.rs#L254)。同样，池内地址连续也不保证一条 FIFO 的节点按顺序紧挨着；按品种组织池、尽量复用附近节点，才有机会改善实际访问的局部性。

复用槽位以后，旧 handle 可能恰好指向一张新订单，因此 handle 同时保存槽位和 generation。每次复用增加 generation，使用前做比较；回绕、日切以及迟到请求由 epoch 和协议去重一起处理。32 位索引、空值哨兵和 generation 都有表示范围，容量配置要落在这个范围内。

省掉分配并不是把容量变成无限。100 万个 64 B 节点约占 61 MiB，ID 索引和输出缓冲还会继续增加工作集。分片检查并预留本次操作需要的节点后，再修改订单状态；容量不足时按预定规则拒单，入口根据容量反馈限流或暂停接单，避免撮合到一半才临时扩容。面向行情重建的接收端则要缓冲并补齐交易所事件，保持盘口完整。

查询入口的临时对象也值得检查。例如，用较长的字符串订单号查哈希表时，若先从 `string_view` 复制成 `string`，查询本身就可能分配内存。让索引支持异构查找，直接接受字符串视图，可以省掉这份临时对象；存储在索引中的键仍要有足够长的生命周期。[低延迟 C++ 中的查询分配优化](https://david-grs.github.io/low_latency_presentation/)。

## 7　按市场规则分开撮合路径

价格索引和节点布局确定以后，普通连续竞价的成交循环可以很短：取对侧最优订单，检查价格能否成交，扣减双方数量，输出成交；订单耗尽就摘掉，价格层清空就推进到下一档。价格时间优先的普通挂单沿 FIFO 处理，主要成本跟实际成交的订单数一起增长。

把所有市场、订单类型和交易阶段都塞进这个循环，每处理一张对手单就会重复检查很多无关条件。可以在接单时确定市场和订单类型，在进入撮合循环前选择对应实现。固定 tick 的普通限价单走一条路径，集合竞价、比例分配、冰山单等分别处理；不同实现共用订单池和价格索引。

A 股的连续竞价和集合竞价就适合这样拆开。集合竞价期间允许买卖挂单交叉：先计算买价 ≥p 的累计买量 B(p)、卖价 ≤p 的累计卖量 S(p)，再依据 `min(B(p), S(p))` 和其他规则确定统一成交价。连续数组可通过累计量扫描完成这一步，再按优先级分配订单。沪深对并列价格的裁决还有差异：沪市比较规定的未成交量，仍并列取中间价并按 tick 规则处理；深市进一步按规定的累计量差和参考价格选择。把它们写成各自的定价函数，比在连续撮合的每次循环里检查“现在是不是集合竞价”更清楚。[沪市规则 3.5.2](https://www.sse.com.cn/lawandrules/sselawsrules2025/trade/universal/c/c_20260424_10816492.shtml)、[深市规则 3.4.3](https://docs.static.szse.cn/www/lawrules/rule/trade/current/W020260424690713155663.pdf)。

日涨跌停边界也与申报价格检查分开。价格笼子限制的是当时新申报的价格，基准会随盘口变化；数组要容纳的是当日仍然有效的全部挂单。因此可以用静态涨跌停价分配数组，再用实时基准校验新单，而不必随价格笼子移动整个存储窗口。沪主板、深市与科创板的相关公式存在区别，按对应规则选择检查函数。[沪市 3.3.14、6.8](https://www.sse.com.cn/lawandrules/sselawsrules2025/trade/universal/c/c_20260424_10816492.shtml)、[深市 3.3.16](https://docs.static.szse.cn/www/lawrules/rule/trade/current/W020260424690713155663.pdf)。

同价位也不总是取队头。CME 的部分产品采用 pro-rata、LMM 或混合分配，处理时要读取总量、计算份额、舍入并分配余量；Coinbase 的正式规则还包括显示量与隐藏量的优先级。价格索引仍然可复用，但档内算法随产品变化。[CME 分配步骤](https://cmegroupclientsite.atlassian.net/wiki/spaces/EPICSANDBOX/pages/457218521/CME+Globex+Matching+Algorithm+Steps)、[Coinbase 交易规则](https://www.coinbase.com/legal/trading_rules)。

在 C++ 中，交易日内固定的规则可在创建订单簿时选好具体类型，撮合路径通过模板或专门函数实现；会变化的交易阶段则通过有序控制消息切换。这样既给编译器内联和删除无关分支的机会，也保留了准确重放当时规则的条件。实际收益取决于分支和代码体积，单纯把运行时判断全部改成模板，也会增加指令缓存压力。

## 8　用单写者减少簿内争用

假设一个线程正在撤销 B，另一个线程正在把 B 的最后 50 股成交。它们都要修改订单剩余量、前后节点、价位总量、ID 索引，还可能删除整个价位。即使每个容器都能并发访问，这一组修改也要确定先后，否则就会出现一边报告撤单成功、另一边又把同一数量成交的问题。

让两条命令进入同一个序列，由一个线程依次处理，能直接消除簿内这些写冲突。一条命令处理完，再处理下一条；订单、价位、索引和位图都由这个线程修改。查询线程消费快照或事件，在自己的副本上读盘口，避免与撮合线程同时读写节点。

FOK 更能说明这个选择的价值。支持 FOK 的引擎先确认能够全量成交，再真正执行；预检与执行采用相同的价格保护、自成交防护、隐藏量处理和分配规则；复杂条件可以先生成有界的执行计划。在单写线程中，两遍扫描之间不插入其他命令，看到的订单状态就保持一致。多写者方案则需要保护整个跨价位操作。OrderBook-rs 虽然使用并发 SkipMap、DashMap，FOK、STP 等路径仍有整簿独占 gate。[跨价位操作的同步](https://github.com/joaquinbejar/OrderBook-rs/blob/54df8ebcd99b4b3fb7373cf848b76e89da1b1361/src/orderbook/book.rs#L426)。

并行放到不同品种之间：一个分片由一个写线程负责，管理一组订单簿；热点品种可以单独分配核心。线程固定在某个 CPU，订单池也在对应 NUMA 节点分配，减少状态在核心和插槽之间迁移。单个热点品种的上限仍然取决于它的顺序处理能力。

入口和出口仍要跨线程传递数据。单生产者、单消费者通道可用预分配 SPSC ring；生产者先写槽位内容，再发布写入位置，消费者确认可读后再访问内容。C++ 中通过对应的 release/acquire 操作同步，并在生产者复用槽位前确认消费者已将它释放。各自频繁修改的计数器分开放置，减少同一缓存行在两个核之间来回传递。LMAX Disruptor 将存储、序号和消费者依赖分开设计，正是为了减少这些共享写入。[Disruptor 原始论文](https://lmax-exchange.github.io/disruptor/disruptor.html)。

多个网关进入同一分片时，还要决定命令合并顺序。接收序号确定 FIFO 的先后，轮询策略影响各入口的等待时间；它们不应由线程调度偶然决定。小批量处理可以摊薄发布位置和跨核通信的成本，但如果为了凑批而等待，就增加了第一条消息的延迟。

按品种拆分后，同一账户仍可能同时在多个分片下单。若各分片独立读取同一余额并批准，就会重复使用资金。可以先分配可独立使用的额度，或由账户服务预留后再放行；涉及跨品种原子成交的组合单，则需要跨簿协调。这也是简单按品种并行的边界。[JX 对跨产品操作的讨论](https://www.janestreet.com/tech-talks/building-an-exchange/)。

## 9　让日志复制与撮合并行

撮合线程已经生成一笔成交，如果紧接着同步写日志、等待副本、编码行情，再向每个客户发送消息，它就要等这些操作结束才能处理下一条命令。订单簿中的一次减量再快，也抵不过后面串行等待的时间。

可以把同一条有序输入同时交给撮合线程和日志复制线程。撮合线程生成状态变化与成交事件，日志线程保存恢复所需的输入和规则版本；发布线程等待两边完成，再按顺序发出确认。这使内存计算与日志复制重叠，但保留了“什么时刻可以告诉客户交易已完成”的条件。Jane Street 的 JX 分享从成交回报会触发客户后续交易这一点，解释了可靠性与复制为何直接影响系统设计。[How to Build an Exchange](https://www.janestreet.com/tech-talks/building-an-exchange/)。

![每个分片单写者的撮合、日志复制与提交发布流程](https://raw.githubusercontent.com/Obscurepawn/TradingSystemLearning/main/hft/assets/orderbook-matching-engine/matching-pipeline.png)

例如第 1200 条命令已经执行完，但日志只满足了前 1199 条的提交条件，发布线程就暂不发出第 1200 条的最终确认。等提交进度追上，才允许发送。副本收到内存和副本已经持久化，对掉电的保证不同；选择哪一种，要与接口承诺一致。单进程竞赛代码生成一次成交回调时，可以省略这一整段工作，生产服务则要把它算进确认延迟。

日志也可以批量写入，发布也可以批量推进序号。收益是摊薄固定成本，代价是批内等待；有界队列则限制撮合线程可以领先多少，避免日志或下游变慢时积压无限增长。行情编码、客户端连接和审计输出各自消费已经提交的事件，慢消费者按服务规则触发背压或断开重连。

制作恢复快照时，在选定序号处保留一份状态，等该序号提交后再确认这份快照可用于恢复。恢复时从快照重放后续已提交日志，使用稳定事件 ID 重发尚未确认送达的结果，接收方按 ID 去重。查询副本也按允许发布的进度更新，避免提前暴露尚未提交的成交。主备切换通过任期和 fencing 撤销旧主接单、发布的权限，新主从已提交的输入继续。一张主动单可能产生很多笔成交，执行前检查或预留足够的输出空间，避免处理到一半才发现回报没有地方保存。

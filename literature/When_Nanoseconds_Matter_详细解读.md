## 1. 为什么做市系统同时需要“快”和“算得对”

### 1.1 速度影响执行，也影响判断所依据的信息

演讲从做市出发：系统持续提供买卖报价，承担库存和价格变化风险。行情改变后，旧价格的合理性也可能改变。如果系统更新得慢，它可能仍在依据过时的订单簿或估值报价。

因此低延迟有两个作用：一是更早执行决策，二是让决策尽量基于新鲜状态。只加速发单而不加速行情处理，无法消除陈旧输入；只把估值算得精细而让结果迟迟不能送达执行端，也可能失去意义。

这解释了为什么演讲不断把局部优化放回完整路径：

```mermaid
flowchart LR
    A[交易所行情] --> B[网卡与接收路径]
    B --> C[解码与订单簿更新]
    C --> D[本机广播]
    D --> E[策略与估值]
    E --> F[执行规则或下单]
    F --> G[交易所]
```

这张图是本文对演讲的概念整理，省略了恢复、风控和其他生产组件。后文的几十纳秒测量只覆盖其中某个局部，不能直接当成完整 tick-to-order 延迟。

### 1.2 FPGA 很快，为什么 C++ 软件仍要快

演讲展示了软件策略层与超低延迟执行层的分工：软件能够运行更复杂、更新更灵活的模型，再把可快速判断的规则交给执行层。讲义给出的示意量级是策略层约 1–10 μs、超低延迟执行低于 1 μs；它们用于解释架构，并非对任意系统的保证。

FPGA 可以很快执行既定规则，但规则本身可能来自软件。如果软件迟迟没有把新行情转化成新阈值，硬件执行得再快，执行的仍是旧判断。所以“已经用了 FPGA”并不意味着软件行情链路可以不计延迟。

还有一个更朴素的约束：网卡接收缓冲有限。处理能力在突发行情中跟不上输入时，问题会从“决策慢”升级为积压、丢包和状态恢复。评估订单簿实现时，需要同时考虑单次耗时和高峰输入下的处理能力。

<a id="sec-2"></a>
## 2. 订单簿：为什么 O(n) 最后胜过 O(log n)

这一部分应连起来看。最终的线性搜索依赖前面做出的连续布局、存储方向和数据分布判断，不能单独抽出来作为普遍结论。

### 2.1 先区分“价格档位”和“一笔订单”

价格档位记录某个价格上的聚合数量；订单则还有自己的 ID、方向、价格与剩余数量。一档价格可以包含很多笔订单。

例如买方 100 元档位有订单 A 的 10 股和订单 B 的 20 股，总量为 30。A 改为 6 股后，档位应减去 4，变成 26；随后 B 撤单，档位变成 6，而不是整个删除。只有该价格聚合数量归零时，才删除价格档位。

这意味着程序有两个不同的定位问题：

| 索引 | 回答的问题 | 典型内容 |
|---|---|---|
| 价格索引 | 这个价格在哪里？邻近档位、最优价格是什么？ | 买卖两侧有序的价格与聚合数量 |
| 订单 ID 索引 | 这次修改或撤单影响哪笔旧订单？ | 方向、价格、原数量，或稳定的档位定位信息 |

在演讲采用的订单级消息语义中，修改和撤单需要通过 ID 恢复旧状态。这里需要的是 **ID 到订单状态的索引**；哈希表是本例的实现选择，不应扩展为所有行情协议都必须使用哈希表。只提供价位聚合增量的协议，会有不同的数据维护方式。

### 2.2 初版采用 map，有合理的工程理由

`std::map` 按价格查找和插入为 O(log n)。在不删除目标元素的前提下，相关迭代器具有稳定性，因此订单 ID 索引可以保存指向价格档位的迭代器。找到订单后，修改可以直接定位；按已知迭代器删除档位为摊还常数，不必重新按价格搜索。订单 ID 哈希查找本身仍是另外一部分成本。

它让接口和实现都很自然，并非一个故意设计得很差的基线。第一次测得的订单簿更新中位延迟约 33 ns，也相当漂亮。

问题是，这个结果同时受到了堆分配布局的帮助。节点若恰好分配得比较紧凑，CPU 访问它们时可以获得较好的缓存局部性；把它看成树结构在所有实际运行环境中的固定成本，就会高估其稳定性。

### 2.3 先改变实验条件，才看见节点布局的代价

演讲在分配过程中引入随机扰动后，map 的中位延迟约从 33 ns 上升到 63 ns。

原因链条是：节点分散 → 遍历需要跨越更多不连续地址 → 下一节点地址依赖当前节点内容 → CPU 难以像连续数组那样提前取数。节点中的管理信息还增加了单位有效数据占用的空间。

这里并不能推出“map 一定会慢一倍”。更可靠的结论是：**容器性能依赖分配和访问历史；基准中偶然良好的堆布局，可能掩盖部署后的成本。**

这次基准回放了一周、数十只大型股票的行情，保留了比固定插入循环更真实的更新分布。它仍然没有复刻整个生产环境。真实输入和堆扰动分别改善了基准的两个方面，不能把它们当成“已经与生产完全相同”的证明。

### 2.4 vector 的优势来自内存布局，代价也必须一起承担

把价格档位放进紧凑的有序数组后，二分查找仍是 O(log n)，中间插入和删除会搬移元素，是 O(n)。为什么这样的组合反而更快？

演讲所举的规模约为单边千级档位。连续数据能让一条缓存行包含多个档位，降低指针追踪；搬移紧凑元素也常有比多个随机节点访问更好的实际效率。而且大部分“更新订单”未必创建或删除档位，只是修改已有档位的数量。

但是不能只替换价格容器，留下原来的订单索引。vector 插入、删除或扩容会使相关迭代器失效。一个常见误区是以为调用 `reserve()` 后就可以永久保存元素地址：它只能避免容量足够时的重新分配，无法阻止中间插入、删除造成的位置移动。标准明确区分了这两类失效情形。[C++ vector 修改操作规则](https://eel.is/c++draft/vector.modifiers)

因此，本例需要让 ID 索引保留方向、价格和数量，再按价格重新定位档位，或者采用另一套经过证明的稳定定位方案。它是在重新分配成本，而不是免费取得两种容器的全部优点。

官方图中普通 vector 的中位延迟约为 **34 ns**。知乎文章一有一处写成约 33 ns，本文统一按讲义图表记录。

### 2.5 把最频繁变化的位置放在数组尾部

vector 已经减少了随机访存，却仍然可能搬移很多数据。下一步要问的是：**真实行情经常修改哪个位置？**

演讲中的分布图显示，更新大量集中在最优买卖价附近。如果把最优价格放在数组头部，一次靠近最优价的新档位插入，可能让后面许多档位都往后挪。

将存储顺序反转，让最优价靠近尾部，就改变了这个成本。以下是本文用于解释的简化买方示例：

```text
最优价在头部：[100, 99, 98, 97, 96]
插入 101：    [101, 100, 99, 98, 97, 96]  需要挪动原有元素

最优价在尾部：[96, 97, 98, 99, 100]
插入 101：    [96, 97, 98, 99, 100, 101]  容量足够时可直接追加
```

真实更新不总是恰好追加，但只要热点集中在尾部附近，平均搬移距离就会缩短。展示订单簿时仍可按最优价优先的顺序读取，无须让展示顺序决定内部存储顺序。

这一步将中位延迟从约 34 ns 改善到 32 ns。更值得注意的是更新成本分布发生变化，而不仅是中位数少了 2 ns。

### 2.6 无分支二分：为什么更多指令也可能更快

连续布局之后，演讲使用性能计数器继续寻找问题。Top-Down 指标显示，前端和错误推测都值得排查；随后将采样定位到代码和汇编，发现搜索路径中的分支成本。

二分搜索每次比较后决定下一半区间。如果输入使方向难以预测，CPU 可能在错误路径上做了工作，再清空并重新开始。无分支版本尝试使用条件选择等指令，减少这种错误推测。

演讲对应的计数器结果约为：分支预测失败从 4,824 万降到 2,783 万，总周期从 39.2 亿降到 35.3 亿；退休指令数略有上升。订单簿更新的中位延迟约降至 29 ns。

这些结果组合在一起，才构成较有说服力的解释：不是因为“指令少了”，而是增加的一点确定工作，比错误推测所浪费的周期便宜。

也不能把源码里没有 `if` 等同于机器码里没有条件跳转。编译器可能把等价写法编译成不同指令，演讲甚至展示了为影响 GCC 生成条件移动而调整表达式的例子。是否达到目的，需要检查目标编译器生成的汇编并重新测量。

### 2.7 为什么线性搜索还能再赢一次

二分搜索比较次数少，却会在数组不同位置之间跳转，而且下一步位置依赖前一步比较。从最优价一侧开始线性扫描，可以利用两个本例已经具备的条件：数据连续，且大部分更新位置离这一端很近。

它并不是每次把一千个档位全扫一遍。假如大量请求在最前面的少数热点档位就停止，实际访问的元素数远小于最坏情况 n。

用本文的分析记号表示，设从热点端开始的命中深度为 K，线性搜索的平均检查量与 E[K] 有关；O(n) 描述的则是最坏情况随总规模的增长方式。它们并不矛盾。连续访问、可预测的控制流和较小的 E[K] 可以共同超过二分搜索在比较次数上的优势。

最终实验中，线性搜索版本的订单簿更新中位延迟约为 22 ns。问答同时指出，更大的集合或不同分布可能改变结论。深档位均匀更新、档位达到十万级、或者频繁需要全簿操作时，都应重新比较。

### 2.8 把完整实验链条放在一起

| 阶段 | 更新中位延迟 | 对应解决的问题 | 讲义图表编号 |
|---|---:|---|---:|
| 原始 map 基准 | 33 ns | 起始测量，局部性较有利 | 30 |
| 随机扰动堆分配后的 map | 63 ns | 暴露节点布局依赖；这是改变基准条件 | 31 |
| 连续 vector | 34 ns | 降低随机指针访问和节点开销 | 37 |
| 反向 vector | 32 ns | 让频繁变化的位置靠近尾部 | 41 |
| 无分支二分 | 29 ns | 减少搜索中的错误推测 | 50 |
| 从热点端线性搜索 | 22 ns | 同时利用更新集中、连续访问和简单控制流 | 54 |

这里有两个口径不能混淆：33→63 是揭示基准的敏感性，不是一次失败的优化；后面这些数字属于订单簿更新路径，不是单次比较、纯搜索函数或整个交易系统的延迟。

## 3. 数据排好了，机器码还可能把收益花掉

### 3.1 热代码的空间也有限

CPU 不只缓存数据，也缓存和解码指令。检查失败后的详细报错、格式化信息、很少执行的恢复逻辑，如果和主路径挤在一起，会让热代码变大，增加取指与布局成本。

演讲展示了将错误处理放入带 `noinline`、`cold` 属性的调用路径，并使用 `[[likely]]` / `[[unlikely]]` 表达常见分支方向的做法。其目的不是删掉检查，而是让常见路径紧凑，少执行的代码留在外面。

这些提示表达的是对工作负载的判断。一个被标为“不太可能”的分支如果在真实行情中频繁发生，提示就失去依据。修改后仍需确认代码布局和测量结果，不能把标注数量当成优化成果。

### 3.2 inline 关键字、内联展开和类型擦除是三个问题

先补充一点语言背景：`inline` 在 C++ 中具有语言层面的定义与链接语义，并不强制编译器把函数体展开到调用点；原演讲没有展开这套语言规则。这里真正影响性能的是优化器在具体构建中做了什么。

对于每次档位搜索都调用的比较器，如果具体 lambda 或函数对象类型保留在模板参数里，编译器更容易看到实现，展开比较并传播常量。经过 `std::function` 类型擦除后，调用通常更难直接分析，还可能留下间接调用。

所以值得问的是：这个极热的回调是否需要运行时替换任意可调用对象？若不需要，保留具体类型可能帮助优化；若确实需要，类型擦除带来的灵活性可能仍值得付出成本。不能把它扩展成“项目里禁止使用 std::function”。

这部分与订单簿例子的联系是：一个看似便宜的比较器会被反复调用，其调用形式可能改变整段搜索能否优化。性能审查不能停在容器名字上。

## 4. 从网卡到策略：通信路径中的语义成本

### 4.1 内核旁路是一组分层选择

演讲沿着网络接口的抽象层级比较了不同方案：

| 路径 | 保留的便利 | 应用接管的工作 |
|---|---|---|
| BSD socket | 成熟的内核网络接口和通用行为 | 相对较少，但经过内核收发路径 |
| OpenOnload 一类用户态协议栈 | 可兼容许多 socket 调用，可通过加载库接入 | 依赖适配的网卡与软件环境 |
| TCPDirect | 更直接的低延迟用户态网络接口 | 更多显式资源与收发管理 |
| ef_vi / DPDK 一类较低层接口 | 对包和队列有更直接的控制 | 协议处理、buffer 生命周期及资源管理等责任增加 |

这不是要求每个系统都走到最底层。降低抽象层级可能去掉系统调用、额外调度或复制等成本，同时把原本由通用组件承担的职责交给应用。

讲义引用了厂商的特定网络基准，但其中的亚微秒数字不能当作任意机器的接收延迟，更不能当作交易系统端到端成绩。更实用的迁移方式，是先确认网络入口在自己的预算中占多少，再判断接管这些职责是否值得。

### 4.2 同机数据分发适合从“共享哪块内存”出发

行情已经进入本机后，多个策略进程可能都需要同一条更新。如果继续走通用 socket，本机数据还可能经过额外的接口、缓冲和复制。共享内存则允许不同进程映射同一批物理页，把问题转化为明确的发布与读取协议。

多进程还提供故障与升级边界：策略进程出问题，不必让行情接收和所有其他策略一起退出。不过共享内存会跨越正常的对象封装边界，需要把协议写清楚。

演讲展示的头部包括协议名称、magic、版本、区域大小和队列容量等。它们帮助接入者识别自己打开的区域，发现不兼容布局，避免把旧格式当新格式解析。

知乎文章进一步强调：不同进程的映射地址不必相同，跨进程消息不能直接携带仅在发送进程有意义的裸指针；偏移、长度、对齐和对象生命周期都应属于协议。跨进程原子操作的 ABI、对齐与平台支持也需要单独确认。这些是文章的工程补充，不能说成原演讲已证明了任意平台上的可移植实现。

<a id="sec-5"></a>
## 5. FastQueue：先写清楚“广播”的约束，再谈无锁

### 5.1 它不是任意语义的消息队列

这一案例的要求非常具体：单生产者、多个消费者；每个消费者都应看到同一消息；容量有界；消息为可复制的变长数据；慢消费者不能无限阻塞生产者。

这里的 SPMC 是广播，而不是把任务分配给其中某一个 worker。把一条消息给所有策略，与让一个 worker 领取一个任务，成本和正确性约束都不同。因此演讲没有拿单播队列的成绩来代替广播队列的比较。

慢消费者会带来一个无法靠名字消除的选择：如果既不允许丢消息，又不允许无限扩容，就必须在某处处理回压。FastQueue 选择让写者继续前进，落后消费者可能被覆盖，随后需要检测和恢复。其性能必须连同这一语义理解。

### 5.2 两个计数器都由生产者更新

最容易读反的地方是计数器命名。`read_counter` 并不是消费者共同推进的读指针。

| 状态 | 谁更新 | 含义 |
|---|---|---|
| `write_counter` | 生产者 | 已预留、可能即将覆盖到的位置上界 |
| `read_counter` | 生产者 | 已经写完并发布的位置上界 |
| 消费者本地 cursor | 对应消费者 | 自己下次要读取的逻辑位置 |

两个全局计数器单调增长，物理地址再映射到环形存储。它们把“空间可能被写者占用”和“内容已经可读”分开了。

概念上的写入顺序是：

```text
公布预留范围 → 填写消息长度和内容 → 公布完成范围
```

读者根据完成上界判断是否有数据，同时使用预留上界判断自己是否已经被绕环覆盖。已发布不代表永远有效：一条老消息即使早已发布，也可能已经被新数据占用了位置。

设队列容量为 Q，本地起始位置为 c，观察到的预留上界为 W，那么 `W - c > Q` 就提示该位置已落入不可安全保留的旧区域。这个式子仅解释覆盖窗口；完整实现还要处理消息范围、环尾、计数器溢出与并发顺序。

### 5.3 检测覆盖，不等于解决了 C++ 数据竞争

演讲简化的读流程会读取长度、验证覆盖与目标空间、复制内容，再检查是否发生覆盖。讲义同时直接标出了 data race：如果读者正在复制普通字节，写者绕环后正好重写同一片内存，这些访问存在冲突。

`release` / `acquire` 可以用于把已经完成的内容发布给读者，但它们不自动阻止未来覆盖。事后发现“刚才读的时候被覆盖了”，也不能让之前的非原子并发读写重新合法。[C++ 数据竞争规则](https://eel.is/c++draft/intro.races)

这个问题在原视频约 52:17–54:06 和讲义第 91 张已被明确承认。因此这里不提供一个看似可直接投产的完整队列代码。应分别解决：发布顺序、读取期间的存储有效性、落后后的恢复、以及目标平台的并发访问语义。

还要修正一个改写细节：知乎文章二的读取示例没有保留讲义中的目标 buffer 大小检查。长度来自共享区域时，复制前必须检查它是否合法、是否容得下。演示还省略了环尾处理。拿走设计思想之前，应先识别这些省略项。

检测到覆盖后的行为也要独立设计。无数据可以稍后再试；已落后则可能需要重定位、请求快照或重建状态。用同一个返回值表示两者，而外层永远重试，并不会自动恢复一个已经落后的订单簿。

### 5.4 真正的优化方向：少触碰大家都在看的缓存行

即便只有一个写者，共享计数器也不免费。写者更新缓存行后，多个读者持有的旧副本可能失效；读者再次读取时，又会引发一致性流量。

将两个原子计数器放到不同缓存行，能减少它们互相牵连造成的 false sharing。但同一计数器仍由写者和读者真实共享，对齐不会消除这部分通信。

演讲继续做了三类修改。

**第一类是提前预留较大范围。** 写者不必每条消息都推进 `write_counter`，而是一次预留例如 100 KB，在本地推进，快用完时再公布下一块预留范围。平均每条消息约 100 B 时，这可把一次共享写摊到约千条消息上；实际数量还取决于长度字段和填充。

这并不意味着等攒满 100 KB 才向消费者发布。`read_counter` 仍然可以随每条消息完成而前进。减少预留计数器更新频率，与延后发布多条消息，是两种不同的批量化。

它的代价是读者必须更保守地对待旧数据：既然生产者宣布了一个更远的覆盖范围，读者可依赖的保留窗口就缩小了一块。这是在空间余量和一致性流量之间做交换。

**第二类是消费者缓存可读上界。** 如果上一次已经观察到一大段完成数据，而本次只消费其中一小部分，就没有必要每条消息重新加载全局完成计数器。只有本地已知范围用完，才刷新它。

**第三类是紧凑的消息布局。** 控制变量需要缓存行隔离，不代表每条 payload 也要独占 64 B。演讲使用较紧凑的 8 B 对齐以改善空间和顺序访问；这只是案例选择，不是所有数据布局都应使用 8 B 的规则。

这几项优化的共同点是减少共享访问次数与不必要的数据占用。只把 `memory_order` 改得更弱，既不能替代正确性证明，也不一定能解决缓存行在多个核心之间频繁往返的问题。

### 5.5 API 可以决定是否必须多复制一次

若接口要求调用者先生成完整临时 buffer，再传给队列，数据往往要先写入临时区，再复制到队列。

另一种接口先给序列化器一段已经预留的目标区域，序列化器直接写入，完成后再发布：

```text
队列预留目标区域
    ↓
序列化器直接写到该区域
    ↓
写入成功后发布
```

这省掉的是临时区到队列的一次复制，并不意味着数据经过全系统时完全零复制。失败时如何取消预留、回调能否抛异常、何时允许消费者读取，也都是接口的一部分。

演讲还提出批量提交和远端 NUMA 节点控制头复制等方向。批量提交可能降低控制开销，也可能增加第一条消息的等待时间；NUMA 优化还要处理额外的状态传播。这些都需要独立测量，不能只因减少了一次访问就断言端到端更快。

### 5.6 怎样读队列性能图

原实验使用 AMD EPYC 9474F、隔离核心、73 B 消息、8 MB 队列，并比较特定的 Aeron C++ 广播组件、Java Disruptor 和 SeqLockQueue 等实现。

FastQueue 的优化有收益，但在不同读者数量下并非始终领先；部分区间中 SeqLockQueue 更好。这张图首先回答的是这组负载下的广播性能，不能把吞吐峰值直接当成 p99 延迟，也不能证明某个实现适合所有消费者数量。

问答进一步澄清，队列不承担持久化和崩溃恢复。一个内存广播结构与提供可靠投递、日志和恢复的系统，完成的工作不同，不能仅凭单条延迟把后者判为多余。可信本地进程的假设也不能直接变成面向恶意输入的安全协议。

<a id="sec-6"></a>
## 6. 性能测量：避免用整个进程的忙碌解释一次决策的延迟

### 6.1 首先定义究竟在测哪一段

加载行情、创建索引和预热缓存可能花很长时间；真正要优化的却是初始化之后的一次订单簿更新。如果从程序启动就采集全部计数，最后的结果可能主要描述加载和分配。

演讲在初始化完成后，再让 perf 附着到运行基准的进程。fork/exec 只是其中一种实现方式，核心是把测量窗口对准目标阶段。它适合持续数秒或数分钟的基准，而不是把附着操作塞进一个只有几十纳秒的测量区间。

同样，“程序用了多少 CPU”和“一次消息处理花了多久”是两个问题。一个一直忙轮询的线程可以占满一个核心，却并没有一直执行策略计算。

### 6.2 Top-Down 用来缩小调查范围

演讲先看较宽泛的 CPU 指标，再定位具体代码，而不是一开始就断定瓶颈来自缓存。

| 类别 | 它提示什么 | 不能据此直接推出什么 |
|---|---|---|
| Retiring | 有多少流水线槽位对应最终退休的指令工作 | 这些工作全部对业务有价值 |
| Bad Speculation | 错误推测、回滚等浪费是否明显 | 应删除所有条件判断 |
| Frontend Bound | 指令供应是否不足，例如取指、解码相关限制 | 一定是数据 cache miss |
| Backend Bound | 数据依赖、内存或执行资源是否限制推进 | 一定要换内存或增加核心 |

Retiring 尤其容易被描述得太乐观。执行了一段多余的复制或计算，指令一样可以正常退休；“没有被 CPU 丢弃”和“对业务必需”不是同一件事。

这些比例是特定计数模型下的流水线分析，不是四种函数墙钟耗时的精确分摊。计数器与 metric 名称还依赖 CPU 和工具版本。

### 6.3 从统计到归因，需要一条证据链

演讲中的分析过程可以整理为：

```text
perf stat：先看瓶颈类别
    ↓
perf record / report：寻找持续出现的热点函数
    ↓
perf annotate：核对源码、基本块和机器指令
    ↓
修改实现，再比较延迟与相关硬件计数器
```

例如怀疑分支预测失败后，需要看到热点确实落在搜索的比较与跳转上，再观察无分支版本是否减少错误推测、降低周期，并改善目标延迟。只有“分支少了”或“某个 counter 下降”，都不足以完成归因。

分析时应保留接近部署的优化构建。知乎解读补充了 `-O3 -g -fno-omit-frame-pointer` 这组选项，思路是在优化代码上保留符号和可用的调用栈信息；它不是原讲义展示的命令。若改用 `-O0`，内联、循环、寄存器分配都可能改变，测到的可能是另一份程序。额外构建选项本身也要评估对结果的影响。

### 6.4 稀疏短函数为什么会躲过采样

考虑一个策略循环：不断 poll 网卡，偶尔处理一次行情，极少数情况下下单。一次判断可能只有几十或几百纳秒。周期采样完全可能一直落在 poll 上，而没有命中那次短暂的下单计算。

这并不是 profiler 给了假结果。它正确描述了 CPU 时间大多花在哪里，只是用户想知道的可能是“每次策略判断的 p99 是否超过预算”。采样热点图没有自动回答这个问题。

因此需要按目标选择手段：

| 目标 | 更适合的手段 | 主要注意点 |
|---|---|---|
| 持续基准的总体瓶颈 | perf 统计与 Top-Down | 窗口不混入初始化 |
| 哪些函数持续消耗 CPU | 采样 profiler | 稀疏短函数可能样本不足 |
| 已知区间的逐次延迟分布 | 显式时间戳或作用域插桩 | 计时与记录本身有开销 |
| 同一构建中按需打开函数跟踪 | XRay 一类动态插桩 | 编译时必须已经预留测点 |

### 6.5 ScopedTrace 的关键不只是“两次读时钟”

演讲用 RAII 作用域在进入和退出时读取 TSC，记录区间与元数据，再交给后台线程汇总。热路径上不应顺手完成字符串格式化、文件写入或同步网络发送，否则会把测量器变成主要负载。

从这一思路出发，实际实现通常需要预分配的线程本地记录区、明确的写满策略和异步导出。即使把 I/O 放到另一个线程，也要检查该线程是否通过共享缓存行、内存带宽或队列回压反过来干扰被测路径。

原示意代码中的两次裸 `__rdtsc()` 不是完整的精密计时实现。时间戳是否真正夹住目标操作、编译器和 CPU 是否重排、TSC 如何换算、线程是否迁移，以及打点开销占多大比例，都需要处理。这里属于本文的计时补充，可结合已有的[时钟专题](../hft/HFT_Engineering_04_高频交易系统中的时钟.md)阅读。

为了避免“测得越细，程序越不像原来”，应先选少量关键边界，并比较插桩关闭和开启时的整体分布。给每个小函数都添加入口出口记录，不一定增加有效信息。

### 6.6 XRay 解决的是不断修改测点的工作流

手工插桩有一个反复出现的成本：发现新怀疑点 → 修改源码 → 构建 → 部署 → 再测。偶发问题如果发生在未预料的路径上，这个循环尤其慢。

XRay 在编译阶段给符合条件的函数预留入口、出口插桩区域；运行时可以将这些区域切换为调用处理函数。于是同一个已插桩构建可以按需开启跟踪，而不必每次都改业务代码。

它不能给任意未准备的二进制凭空补齐全部测点。LLVM 文档还说明，默认启发式会选择至少约 200 条指令或含循环的函数；非常短的热点函数可能需要调整阈值或显式标记。handler 自身应避免再次被插桩，并保持足够轻量。[LLVM XRay 官方文档](https://llvm.org/docs/XRay.html)

因此 XRay 与 perf 是互补关系：前者帮助切换详细跟踪，后者擅长从总体执行中找方向。运行时开关方便，也不等于开启后的记录成本可以忽略。

<a id="sec-7"></a>
## 7. 一次跑分快，不代表系统能长期保持快

### 7.1 指标必须关联预期，而不只是画图

演讲把“保持快”作为独立工程问题。代码、编译器、行情分布和同机进程都会变化，一次优化可能在几个月后悄悄退化。

仅把数值写入数据库，并不能保证有人发现问题。需要明确哪些边界要守住，出现何种偏离时触发检查。本文将这一要求具体化为一份结果记录：

| 应保存的内容 | 为什么有用 |
|---|---|
| 测量起止边界 | 防止不同版本实际测了不同区间 |
| 输入与更新分布 | 判断是算法回退还是工作负载改变 |
| 硬件、核心与同机部署 | 解释跨环境差异 |
| 样本量、分位数与时间窗口 | 判断尾部结果是否可靠 |
| 绝对预算与历史基线 | 同时发现超预算和逐步回退 |
| 对应代码与构建信息 | 让异常可以被复查 |

这些字段是本文的实施建议，不是演讲给出的唯一标准模板。阈值也应从系统目标确定，不能替所有系统统一规定一个纳秒数字。

### 7.2 没有共享业务数据，也会共享硬件瓶颈

演讲最后比较了一个 worker 和六个 worker 的随机内存访问。每个 worker 有自己的数组，固定在自己的核心上，不需要用锁协调业务数据。

但多个核心可能共享 L3、互连和内存资源。当工作集进入某些区间时，六个 worker 的总吞吐相对单 worker 的扩展倍数接近 1，而不是 6。

这说明“没有锁”和“没有资源竞争”之间还隔着整台机器。独立进程占用的缓存会影响彼此，单独测试一个服务时拥有的缓存容量，在真实部署中未必仍属于它。

该实验刻意使用随机访问，结果属于特定硬件与工作集，不能得出“增加核心没有意义”。更合理的做法是把独立运行与预期共置运行都纳入测量，观察在哪个工作集区间开始退化，再决定是否调整布局、放置或进程分工。

### 7.3 问答里的边界同样值得保留

- **混合搜索不是天然更优。** 演讲尝试过先线性、再二分，本例没有赢过简单线性扫描；更大数据集仍可能有不同结果。
- **SoA 和 SIMD 需要收益条件。** 将价格与数量拆开可减少只查价格时的无关数据，也更利于向量化；薄订单簿可能无法摊薄向量路径的启动与处理成本。不是所有对象都应拆成 SoA。
- **持久化是另一种职责。** WAL 是可考虑的数据结构方向，并非要求把所有消息同步写入数据库；队列恢复能力仍需专门设计。
- **受控进程假设不等于安全隔离。** 对恶意共享内存写者的 TOCTOU 问题，演讲者没有给出完整答案。
- **简单实现影响交付速度。** 如果复杂优化带来大量验证和维护负担，其开发周期也应计入工程取舍。演讲结尾把 time to market 也视为一种需要关注的延迟。

<a id="sec-8"></a>
## 8. 延伸阅读：Daniel Anderson 怎样把 sticky counter 从 lock-free 推到 wait-free

本节来自用户提供的第四篇知乎文章及 [When Lock-Free Still Isn't Enough 官方讲义](https://github.com/CppCon/CppCon2024/blob/main/Presentations/When_Lock-Free_Still_Isn%27t_Enough.pdf)。它不是 David Gross 演讲的后半部分。本次核对了该讲义中的算法演进与实验表格，没有把知乎所述的全部现场问答当作独立核实过的逐字记录。

### 8.1 “没有 mutex”没有说明进度保证

Lock-free 关注系统整体：有线程持续执行操作时，系统能持续完成操作，但某个线程可能反复输掉竞争。Wait-free 更强：每个操作都能在有界的自身算法步骤内完成，不因其他线程不断抢先而无限重试。

这里的“有界”不是墙钟时间。操作系统把线程暂停十秒，wait-free 算法无法在它未执行时替它凭空完成所有工作；单条原子指令的实际延迟也受硬件影响。

典型 CAS loop 说明了两者的区别：线程读取旧值，计算新值，再尝试条件提交。如果别人先改了共享状态，它就拿到新值并重试。忽略 weak CAS 允许的伪失败时，失败意味着期间有别的更新成功，因此整体有进展；但没有机制保证下一次一定轮到这个线程赢。

### 8.2 问题规格：归零以后，不能复活

Sticky counter 提供三个操作：非零时尝试加一、减少一个已有计数、读取逻辑值。减少到零的那次操作还应返回一个特殊结果，让调用方承担最后释放的责任。

它对应引用计数中的实际需求。例如尝试从弱引用获得强引用时，必须确认对象仍然存活；计数已经归零后，不能重新加一并假装对象仍然存在。

下面这个交错揭示了为什么两个独立原子操作也不够：

```text
初始计数为 1
A 检查：计数大于 0
B 释放最后一个引用：计数变成 0
A 按刚才的检查结果加一：计数变回 1
```

问题在于“检查”与“更新”没有组成一个不可分割的条件操作。把变量类型改成 atomic，只能保证每个独立操作的原子性，不能自动把组合变成事务。

### 8.3 第一版：CAS loop 正确，但可能一直重试

自然的 lock-free 方案是：读取非零值 v，尝试 CAS(v, v+1)，失败后继续判断新值。C++ compare-exchange 失败会把观察到的值写回 expected，所以空循环中仍然发生了状态更新。

减一可以使用 `fetch_sub(1)`，根据返回的旧值是否为 1，判断自己是否释放了最后一份引用。这里有明确的前置条件：调用者确实持有一份可释放的计数，不能对逻辑零继续减。

为了去掉条件加一的无界重试，演讲接下来改变了共享状态的表示，而不只是把循环次数限制一下。

### 8.4 把“物理整数”和“逻辑状态”分开

64 位状态的低 62 位用于计数，高位用于标志：`IS_ZERO` 表示逻辑上永久归零，`HELPED` 稍后用于记录别人协助完成了归零。

条件加一可以先执行一次 `fetch_add(1)`，再根据旧值中是否已有 `IS_ZERO` 返回成功或失败。若标志早已存在，底层低位即使改变，逻辑上仍为零，不能把低位当成复活的引用。

这要求数值与累计操作都不破坏保留位语义。计数上限、失败加一长期累积后的溢出，以及对象和控制块的存活期，都是生产实现需要另外证明的边界。

减一发现旧值为 1 时，先把物理值减为普通的 0，再尝试将 0 改为 `IS_ZERO`。在这两步之间，一个并发加一可能把物理值改回 1，使归零 CAS 失败。

没有读取操作暴露中间值时，这种重叠执行可以被解释为“先加一、后减一”：从逻辑上的 1 变成 2，再回到 1。它利用了线性化的要求——所有操作应等价于某个符合真实先后约束的串行历史，而不是要求每个中间机器整数都直接对应最终逻辑状态。

### 8.5 加入 read 后，中间状态成为问题

如果 read 直接返回普通 0，随后加一成功，再有 read 返回 1，外部就能看到“先归零、后复活”。这个可观察历史违反 sticky counter 的规格。

不能简单让读者等原减一线程完成：原线程若被暂停，读者也被拖住。演讲选择 helping：read 看到普通 0，就知道有减一过程尚未完成，可以尝试替它设置归零标志。

若这次 CAS 成功，返回逻辑零；若失败，CAS 会带回新状态，read 按它解释即可，不进入无界重试。帮助成立的前提，是共享状态留下了可识别、可由其他线程完成的中间步骤。

### 8.6 改对状态还不够：最后由谁销毁对象

如果 read 只帮忙写入 `IS_ZERO`，原减一线程恢复后发现自己的 CAS 失败，可能返回 false。结果是对象已经逻辑归零，却没有任何减一操作告诉调用方“你负责最后释放”。

因此 read 帮忙时写入 `IS_ZERO | HELPED`，留下一个尚未领取的完成责任。相关减一操作看到它后，执行 `exchange(IS_ZERO)`；只有真正从 exchange 的旧值中拿到 `HELPED` 的操作，才返回“最后释放成功”。

为什么不能只检查自己读到的 HELPED？因为可能有多个减一操作都停在归零附近：减一到 0、加一回 1、另一减一再到 0，然后 read 帮忙。多个线程的本地副本都可能看到 HELPED。必须通过原子 exchange 消费这个共享标记，才能让责任只被领取一次。

| 子问题 | 只做直观修改会怎样 | 演讲的处理 |
|---|---|---|
| 条件加一 | 分开检查和更新会让零复活 | CAS loop；之后改为标志状态与一次 fetch_add |
| read 看见普通零 | 暴露尚未提交的中间状态 | read 帮助提交逻辑零 |
| helper 完成归零 | 原减一可能不再返回最后释放成功 | 留下 HELPED |
| 多个减一看到 HELPED | 可能重复承担销毁责任 | 用 exchange 的旧值唯一领取责任 |

这个例子教的不只是 helping，还包括**状态、返回值和资源释放责任必须一起正确**。只证明共享整数最终是零，还不足以证明引用计数实现正确。

### 8.7 为什么它可以有界，以及哪些问题没有因此消失

在演讲的抽象原子操作模型下，加一只需一次 fetch_add；读取只在普通零附近尝试一次 CAS；减一执行一次 fetch_sub，必要时再执行有限次 CAS/exchange。没有依赖竞争最终消失才能退出的循环。

但这仍以底层原子原语符合模型为前提。`is_lock_free()` 能帮助发现某些实现是否使用锁，却不足以单独证明每条操作在目标硬件上满足所需的有界进度。C++ 内存序、对象生命周期和实际指令实现也不能从“源码里没有循环”自动推出。

压力测试可以找出错误交错，却不能通过“跑了一天没失败”证明所有交错都正确。应结合线性化分析、模型检查或其他合适的证明手段。此处只重建演讲的设计逻辑，没有给出可直接替换标准库引用计数的完整实现。

### 8.8 更强的保证不意味着每种负载下都更快

演讲将两种计数器用于作者自己的 `atomic<shared_ptr>` 实现，比较 load 延迟。下面摘取单路 28 个物理核、使用 56 个硬件线程时的 p99 数据；工作负载按执行 load/store 的线程比例设置：

| 线程分工 | Lock-free 的 load p99 | Wait-free 的 load p99 | 观察 |
|---|---:|---:|---|
| 全部 load | 31.1 μs | 13.3 μs | wait-free 的尾部明显更低 |
| 50% load / 50% store | 26.7 μs | 26.4 μs | 两者接近 |
| 10% load / 90% store | 82.6 μs | 86.4 μs | lock-free 在该点更低 |

这是特定实现的 **load 延迟**，并非标准库所有 shared_ptr 操作的普遍成绩。高 load 竞争时，消除加引用的 CAS 重试具有合理的性能解释；这些表格本身没有把每部分收益独立分解出来，所以仍不能把差异全部归因于某个形式化标签。

与 HFT 的联系属于本文推论：Gross 的队列例子优先减少真实共享访问；Anderson 则展示共享状态无法避免时，如何进一步讨论单次操作的进度和生命周期正确性。它适合启发快照引用等设计讨论，并不意味着应把所有低延迟路径替换成 wait-free 数据结构。

## 9. 把知识迁移到自己的交易系统

### 9.1 与《The Latency Slippage》的互补关系

[另一份详细笔记](The_Latency_Slippage_详细解读.md)沿一个期权重估程序，深入研究批处理、预取、缓存污染和跨核所有权。Gross 的演讲覆盖面更广，解释这些局部问题如何出现在订单簿、消息传输和生产测量中。

| 问题 | Gross 演讲中的体现 | 缓存 PDF 中的体现 |
|---|---|---|
| 输入分布影响设计 | 最优价附近更新集中，改变容器顺序和搜索方式 | 一次事件访问 64 个期权，决定批次和预取安排 |
| 内存访问并非只看总量 | 连续数组胜过节点追踪 | miss 数相近，增加并行后仍能缩短等待 |
| 共享变量存在物理通信成本 | 减少计数器发布和重新加载 | 避免读回共享请求数据，研究脏行交接 |
| 单项指标不能代替结果 | branch miss 下降还要核对周期和延迟 | 缓存操作必须与最终 p50/p90 对照 |
| 部署环境会改变结论 | 同机 worker 争用共享 L3 | 工作集、缓存容量和具体微架构决定收益 |

这些例子并不互相矛盾。订单簿的紧凑结构可能适合简单扫描；较大期权工作集可能需要批处理隐藏 miss；广播控制行则首先面对一致性通信。先识别受限资源，才能选择相应办法。

### 9.2 建议的学习实验：以下均未在本次整理中执行

**实验一：把订单簿的数据分布变成可控变量。** 以正确性参考实现校验 map、vector、反向 vector 和不同搜索方式。分别使用热点集中、均匀深度、深档位突发更新，记录新增、修改、撤单的比例与各自分布。这样可以观察线性搜索在哪些条件下失去优势，而不只复现一个冠军数字。

**实验二：把“预留”和“发布”分开测量。** 对同一正确的广播协议，独立改变预留块大小、发布批量、消费者数量和速度。记录吞吐、端到端分位数、落后恢复次数和一致性相关指标。重点验证增大预留块是否只减少共享访问，以及批量发布是否引入额外排队等待。不要直接把演示中的 data-race 版本当成正确性基础。

**实验三：比较测量器带来的扰动。** 对稀疏事件负载，比较无插桩、少量作用域打点、详细函数跟踪。既观察目标函数样本数量，也观察整体路径分布是否变化。这样可以分清“终于测到了长尾”和“测量器制造了长尾”。

**实验四：复现单进程与共置差异。** 固定业务输入、绑核和内存设置，逐步加入与实际部署接近的其他进程。检查缓存工作集和带宽竞争，判断单独基准中的收益是否仍然存在。

### 9.3 一份值得保留的优化记录应回答什么

后续学习或实现时，每次优化都可以用同一组问题检查：当前业务操作是什么？输入集中在哪里？初版为何合理？哪个实验推翻了直觉？改动减少的是计算、随机访问、错误推测、复制，还是跨核通信？结果覆盖哪个测量边界？换机器或换分布后，哪些条件可能不再成立？

能回答这些问题，才真正学到了演讲的工程方法。单独记住 22 ns、100 KB 或 wait-free，无法说明自己的系统应该怎样设计。
